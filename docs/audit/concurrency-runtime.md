# Audit findings: concurrency-runtime

Review of the `#expectSnapshot` assertion pipeline's concurrency and runtime behavior. The core defect is that the non-main-thread bridge (`DispatchQueue.main.sync` in `ExpectSnapshotAdapter.runOnMainActor`) drops Swift Testing's task-locals; failure recording for the ordinary mismatch path happens inside that block where `Test.current`/`Configuration.current` are nil, so for every non-`@MainActor` test (the default shape, including this repo's own integration tests) snapshot failures become orphaned run-level issues, the failing test reports as passing, and `withKnownIssue` cannot match — a silent parity regression versus the legacy `@SnapshotSuite` path. A related defect drops native usage into pointfree's never-reset process-global file counter, producing order-dependent `.1`/`.2` reference filenames for shared snapshot names and in-process test repetitions. Several lower-severity issues (task-pointer cache key producing fresh contexts for structured child tasks, an unbounded context cache, a process-crashing precondition, dead-code async bridge, inert availability annotations, and a test-coverage gap around these exact paths) round out the report. No new deadlock was found: the `main.sync` design is safe against the runner, and `@MainActor` callers take the `assumeIsolated` fast path which preserves task-locals correctly.

## 1. [HIGH] Snapshot mismatch failures are recorded with `Test.current == nil` inside the `DispatchQueue.main.sync` hop, so they are not attributed to (and do not fail) the invoking test for any non-`@MainActor` test

- **File**: `Sources/SnapshotTestingMacros/Assertion/ExpectSnapshotAdapter.swift:799`
- **Failure scenario**: Any `#expectSnapshot` called from a test that is not already on the main thread (the default: every plain `struct` + `@Test` suite, including all of this repo's own integration tests, e.g. `Tests/SnapshotsIntegrationTests/ExpectSnapshot/ExpectSnapshot+Closures.swift:5`) takes the `DispatchQueue.main.sync` branch of `runOnMainActor`. The ordinary failure path — snapshot mismatch, missing reference, or a record-mode "recorded new snapshot" notice — is caught and reported INSIDE that GCD block by `IssueRecordingAsserter`, where Swift Testing's task-locals (`Test.current`, `Test.Case.current`, `Configuration.current`) are gone. `Issue.record` therefore posts an event with no associated test: swift-testing delivers it via its all-configurations fallback as an orphaned run-level issue, the specific failing test is reported as PASSED, `withKnownIssue { #expectSnapshot(...) }` cannot match the issue (producing a spurious "known issue was not recorded" failure), and under parallel execution the user cannot tell which test produced the failure. Additionally, in the nil-`Test.current` branch of `recordIssue` (`Asserter.swift:122-127`) the error payload is dropped and only the comment is recorded (nil comment for non-`SnapshotError` errors → an empty issue). The legacy `@SnapshotSuite` path does NOT have this bug: its generated `@MainActor @Test` functions structurally `await assertSnapshot(with:)` on the test task, preserving attribution — so migrating to the new native macro silently degrades failure reporting.
- **Evidence**: Chain: (1) `ExpectSnapshotAdapter.swift:787-813` — `runOnMainActor` checks `Thread.isMainThread`; the false branch runs the operation inside `DispatchQueue.main.sync { MainActor.assumeIsolated { ... } }`, a plain queue callout with no current Swift task, so all task-locals read their defaults. (2) The authors know this: `ExpectSnapshotAdapter.swift:762` captures `ResolvedSnapshotRuntimeState.current` on the test task and `:829-830` re-applies the package's six trait task-locals plus `TaskLocalSnapshotExecutionContext.$current` inside the block — but `Test.current`/`Configuration.current` are swift-testing internals that cannot be re-bound. (3) `Asserter.swift:56-88` — `IssueRecordingAsserter.assertSnapshot` catches the `SnapshotError` thrown by `PointfreeAsserter.verifySnapshot` (`Asserter.swift:145-162`, message-returning API, so ALL real mismatches surface here) and calls `recordIssue` immediately, still inside the block; `Asserter.swift:98-127` calls `Testing.Issue.record`, and at `:107` `Test.current != nil` evaluates false on this path. (4) Contrast: errors that escape the block are rethrown across the `SyncMainActorResultBox` (`ExpectSnapshotAdapter.swift:815-819`) and recorded on the test task at `:771-779`/`:921-937` where `Test.current` IS present — correct for makeValue/request-generation errors, showing the in-block recording is an oversight. (5) Integration tests are non-`@MainActor` structs, so this is the mainstream path; the legacy macro expansion (`Tests/SnapshotsUnitTests/SnapshotSuite/SnapshotSuiteTests+Diagnostics.swift:360-380`) generates `@MainActor @Test ... try await SnapshotTestingMacros.assertSnapshot(with: generator)` which stays on the test task (structured executor hop preserves task-locals) — a behaviour parity regression between legacy and native paths.
- **Suggested fix**: Do not call `Issue.record` inside the dispatch block. Have `IssueRecordingAsserter` collect failures (e.g. `[SnapshotError]`) instead of recording, shuttle them back through the existing `SyncMainActorResultBox` alongside the `Result`, and record them after `result.get()` returns on the calling test task (where `Test.current` is intact). For the async overloads, route through a structured hop — the already-written but unused `Asserter.assertSnapshots(from:) async` (`await MainActor.run`) preserves task-locals and fixes attribution outright. Also make the nil-`Test.current` branch of `recordIssue` include the error description in the comment so no payload is lost.
- **needs_dynamic_verification**: true

## 2. [HIGH] Native `#expectSnapshot` path defeats pointfree's per-test file counter: process-global counter assigns order-dependent `.N` reference-file suffixes, breaking same-named snapshots across tests and in-process test repetitions

- **File**: `Sources/SnapshotTestingMacros/Assertion/Asserter.swift:149`
- **Failure scenario**: `PointfreeAsserter` calls `SnapshotTesting.verifySnapshot(... named: nil ... testName: request.testName ...)`. With `named: nil`, swift-snapshot-testing 1.19.1 derives the reference filename suffix from a counter keyed by (snapshotDirectory + testName): first hit → `name.1.png`, second hit → `name.2.png`. Which counter is used depends on `Test.current`: non-nil → the task-local `File.counter` (isolated per test only when pointfree's `.snapshots` trait binds it); nil → a process-global `_counter` that is only reset by an XCTest observer (`testCaseDidFinish`) which never fires in a pure swift-testing process. On the native path BOTH protections are lost: (a) the assertion executes inside `DispatchQueue.main.sync` where `Test.current == nil`, selecting the never-reset global `_counter`; (b) native usage doesn't apply `_SnapshotsTestTrait` anyway (the repo comment says only the deprecated `@SnapshotSuite` macro applies `.pointfreeSnapshots`). Concrete failures: (1) Two tests in the same file that resolve the same snapshot name — an explicit shared `named:` or a shared helper function containing `#expectSnapshot` (the helper's `#function` becomes the baseName, and each test gets its own `SnapshotExecutionContext` so the wrapper's dedup can't see the collision) — get `.1` and `.2` assigned by execution order, which is nondeterministic under swift-testing's parallel scheduling: record mode writes both files with order-dependent content, and subsequent verify runs flap between match and mismatch as ordering changes. (2) In-process test repetitions (this repo ships `Tests/SnapshotsIntegrationRepetitionTests.xctestplan` with fixedIterations=3) increment the global counter across iterations, so iteration 2 looks for `name.2.png` which does not exist — unless the run happens to be hosted in a way where an `XCTestCase` finishes between iterations and fires the reset observer, making repetition support environment-dependent (`swift test` has no such reset).
- **Evidence**: Chain: (1) `Asserter.swift:146-157` — `verifySnapshot(of:as:named: nil, snapshotDirectory: request.snapshotDirectory, ..., testName: request.testName, ...)`. (2) Vendored `.build/checkouts/swift-snapshot-testing/Sources/SnapshotTesting/AssertSnapshot.swift:324-331` — `identifier = String(counter.next(for: snapshotDirectoryUrl.appendingPathComponent(testName).absoluteString))` when name == nil, producing `"\(testName).\(identifier)"`; `:555-561` — `counter` returns `File.counter` iff `Test.current != nil`, else global `_counter`; `:595-609` — `_counter` reset only in `CleanCounterBetweenTestCases.testCaseDidFinish`; vendored `SnapshotsTestTrait.swift:44-59` — only `_SnapshotsTestTrait.provideScope` binds `File.$counter.withValue(File.Counter())` per test. (3) `Sources/SnapshotTestingMacros/Traits/PointfreeSnapshotTesting/PointfreeSnapshots+Init.swift:5-11` — `.pointfreeSnapshots` == pointfree `.snapshots`, applied automatically only by the deprecated macro; "native @Suite/@Test usage should not need to use it directly". (4) `Test.current == nil` inside the hop per finding 1 (`ExpectSnapshotAdapter.swift:799-813`). (5) testName contains no per-test component when `named:` is used: `RequestGenerator/Generators/NameAssertionRequestGenerator.swift:42-51` joins [configurationName, name, size, theme] only, and `snapshotDirectory` is per-file (`AssertionRequestGenerator.swift:51-75`) — so two tests in one file sharing a name share the counter key. (6) Checked-in references are uniformly `.1.png` (`Tests/SnapshotsIntegrationRepetitionTests/__Snapshots__/...`), consistent with each key being hit exactly once per recorded process — the latent drift appears exactly when a key is hit twice.
- **Suggested fix**: Stop relying on pointfree's counter entirely: pass an explicit `named:` (e.g. the wrapper-resolved identifier, or a constant "1") to `verifySnapshot` so the filename is fully determined by the wrapper's own `SnapshotExecutionContext` naming, which is already deduplicated per test context. Alternatively (or additionally) have the native runtime establish pointfree scoping itself. Explicit naming is the robust fix and also makes in-process repetitions deterministic.
- **needs_dynamic_verification**: true

## 3. [MEDIUM] Structured child tasks inside one test get fresh execution contexts, so unnamed-name deduplication breaks and two different snapshots contest the same reference file

- **File**: `Sources/SnapshotTestingMacros/Assertion/TaskLocalSnapshotExecutionContext.swift:50`
- **Failure scenario**: The context cache key includes the raw task pointer (`taskIdentity`). A structured child task (`async let`, `withTaskGroup`, or `Task {}` from the test) inherits `Test.current`/`Test.Case.current` — so `requireActiveTestContext` passes and the call is "supported" — but has a different task pointer, producing a different cache key and thus a fresh `SnapshotExecutionContext` whose `usedNames` set is empty. Two `#expectSnapshot` calls in the same test split across the parent and a child task (or two child tasks) each resolve the undecorated baseName (e.g. `myTest`), yielding identical `testName` values and identical reference paths. Combined with the global pointfree counter (finding 2), the `.1`/`.2` suffix assignment then depends on which render reaches the main queue first — so in record mode the two different views' images land in order-dependent files, and verify runs produce racy false failures or false passes. This is the inverse manifestation of confirmed bug (1): the same task-pointer key design produces stale sharing across recycled tasks AND missing sharing across live sibling tasks; the unit test `childTaskGetsFreshCachedContext` (`Tests/SnapshotsUnitTests/ExpectSnapshot/SnapshotExecutionContextOwnershipTests.swift:56-64`) encodes the fresh-context identity but nothing covers the resulting artifact-name collision.
- **Evidence**: `TaskLocalSnapshotExecutionContext.swift:19-27` derives `taskIdentity` from `withUnsafeCurrentTask` pointer bits; `:50-62` cache lookup keyed by (testID, caseIdentity, taskIdentity) — a child task in the same test case differs only in taskIdentity → cache miss → new context (`:59`). `SnapshotExecutionContext.swift:18-35` — dedup (`-2`, `-3` suffixes) only operates within one context instance's `usedNames`. Both contexts derive the same `baseName` from the same `#function` (`SnapshotExecutionContext.swift:12-16`). `NameAssertionRequestGenerator.swift:42-51` — testName built from that name plus size/theme only, so both snapshots map to the same file path in the same per-file `__Snapshots__` directory (`AssertionRequestGenerator.swift:51-75`). Task-locals (hence `Test.current`) DO inherit into structured children, so `SnapshotRuntimePreconditions.swift:8-14` does not stop this usage.
- **Suggested fix**: Drop `taskIdentity` from the cache key and key by (testID, caseIdentity) alone, with eviction when the test/case scope ends (e.g. via a TestScoping trait or by binding the context in a task-local at test entry). This restores name dedup across all tasks belonging to one test case, and simultaneously fixes confirmed bug (1)'s recycled-pointer staleness and finding 5's unbounded growth. If concurrent sibling-task assertions are meant to be unsupported, detect and record an explicit issue instead of silently colliding.
- **needs_dynamic_verification**: true

## 4. [MEDIUM] `preconditionFailure` on `Test.current == nil` crashes the entire test process for plausible mid-migration and detached-task usage

- **File**: `Sources/SnapshotTestingMacros/Assertion/SnapshotRuntimePreconditions.swift:10`
- **Failure scenario**: `requireActiveTestContext` traps the whole process rather than failing the one offending test. Reachable in realistic, not-obviously-wrong usage: (a) `Task.detached { #expectSnapshot(...) }` inside a genuine swift-testing test — detached tasks deliberately do not inherit task-locals, so `Test.current` is nil while a test is actively running; (b) `DispatchQueue.global().async`/completion-handler bridges that hop off the test task; (c) calling `#expectSnapshot` from an XCTest method during incremental migration — a key audience for this branch's migration CLI (`IssueRecordingAsserter` even carries an XCTFail fallback for Testing-unavailable builds, but Testing-importable XCTest hosts hit the trap first). One such call kills the in-process parallel run for every suite, losing all other results; on CI the crash is far harder to diagnose than a recorded issue with the precondition message would be.
- **Evidence**: `SnapshotRuntimePreconditions.swift:8-14` — `guard let currentTest else { preconditionFailure(activeTestTaskMessage) }`; invoked at the head of every adapter entry point (`ExpectSnapshotAdapter.swift:54, 76, 98, 120, 250, 284, 317, 351, 386, 448`) before any recovery mechanism exists. Detached-task non-inheritance is by design (and demonstrated by the repo's own test at `SnapshotExecutionContextOwnershipTests.swift:34-45`). swift-testing's `Issue.record` outside a test still surfaces via its all-configurations fallback, so a record-and-return failure mode is available and strictly less destructive.
- **Suggested fix**: Replace the trap with a recorded issue plus early return for non-throwing overloads (`Issue.record` with the same message — it surfaces as a run-level issue even without `Test.current`), and a thrown error for throwing/async overloads. If a hard trap is deliberately preferred for API discipline, document it prominently on the macro and keep it out of the XCTest-migration story.
- **needs_dynamic_verification**: false

## 5. [LOW] `SnapshotExecutionContext` cache grows without bound for the process lifetime

- **File**: `Sources/SnapshotTestingMacros/Assertion/TaskLocalSnapshotExecutionContext.swift:32`
- **Failure scenario**: `SnapshotExecutionContextCache.contexts` is insert-only: both `withCurrent` overloads add on miss and nothing ever evicts. Every distinct (testID, caseIdentity, taskIdentity) triple — one per test case in practice, more with child tasks — leaks a `SnapshotExecutionContext` (NSLock + `Set<String>` of used names) for the life of the test process. In large parameterized suites this is a slow unbounded leak; it is also the enabling condition for confirmed bug (1), since stale entries survive to be re-found by recycled task pointers.
- **Evidence**: `TaskLocalSnapshotExecutionContext.swift:30-33` (process-lifetime static cache via `:36`), `:54-62` and `:86-94` (insert-on-miss, no removal anywhere in the codebase — `rg 'contexts\['` shows only the two insert/lookup sites).
- **Suggested fix**: Evict entries when the owning test case completes (TestScoping trait or keying the cache by a scope object), or replace the cache with a task-local context established once per test by a trait — which also removes the task-pointer key entirely (see finding 3).
- **needs_dynamic_verification**: false

## 6. [LOW] `@available(*, message:)` guardrails on public implementation-detail APIs are inert

- **File**: `Sources/SnapshotTestingMacros/Assertion/assertSnapshot.swift:3`
- **Failure scenario**: `@available(*, message: "This is an implementation detail. Do not call this function directly.")` on the public `assertSnapshot(with:)` (and the same pattern on `__SnapshotViewDecoratorConfiguration` at `Sources/SnapshotTestingMacros/Traits/_Types/TestScoping/__SnapshotViewDecoratorConfiguration.swift:10`) emits no diagnostic: an availability attribute with only a message — no `deprecated`/`unavailable` — has no diagnostic channel, so the intended do-not-call warning never reaches users. Users can call the implementation-detail entry points with zero compiler feedback.
- **Evidence**: `assertSnapshot.swift:3-7`; `__SnapshotViewDecoratorConfiguration.swift:10-12`. Swift availability grammar only surfaces `message:` alongside `deprecated`, `unavailable`, or obsoletion; a bare `*` + message is accepted but produces no warning at call sites.
- **Suggested fix**: Use `@available(*, deprecated, message: ...)` (warning) or `@_spi(SnapshotTestingMacrosInternal)` / underscored + `@_documentation(visibility: private)` consistently, matching the approach already used for `__expectSnapshot`.
- **needs_dynamic_verification**: false

## 7. [IMPROVEMENT] The task-local-safe async MainActor bridge exists but is dead code; async overloads instead block cooperative-pool threads in `DispatchQueue.main.sync`

- **File**: `Sources/SnapshotTestingMacros/Assertion/Asserter.swift:20`
- **Failure scenario**: `Asserter.assertSnapshots(from:) async` — which hops via `await MainActor.run`, staying on the same task so `Test.current`, `Test.Case.current`, `Configuration.current` and all trait task-locals survive without any recapture machinery — has no callers. Every async `#expectSnapshot` overload (`runLazyAsync`, `runLazyAsyncThrowing`) still funnels into the synchronous `runOnMainActor`, which parks a cooperative-pool thread inside `DispatchQueue.main.sync` for the full render+compare duration. Under a parallel suite on an N-core machine this can park up to N pool threads at once, serializing on the main queue while starving unrelated async work; it also means any strategy whose fulfillment requires a nested main-queue drain cannot complete inside the queue callout and hits pointfree's 5s XCTWaiter timeout (vendored `AssertSnapshot.swift:343-349`). Wiring the async overloads through the structured path removes the pool blocking and fixes finding 1 for async callers with a one-line change; the declared-but-unusable `throws` on the dead method is a further sign it was never finished.
- **Evidence**: `Asserter.swift:20-24` defined, `rg 'assertSnapshots\(from'` finds no call site; `ExpectSnapshotAdapter.swift:451-466` — `runLazyAsyncThrowing` awaits `makeValue` on the test task then calls the sync `runOnMainActor` (`:454`) instead of an await-based hop; `ExpectSnapshotAdapter.swift:798-813` — the blocking bridge.
- **Suggested fix**: Route `runLazyAsync`/`runLazyAsyncThrowing` through an async MainActor hop (`await MainActor.run` or a `@MainActor` function call), and delete `Asserter.assertSnapshots(from:)` or make it the canonical entry. Keep the `DispatchQueue.main.sync` bridge only for the synchronous overloads, with the failure-collection fix from finding 1.
- **needs_dynamic_verification**: false

## 8. [IMPROVEMENT] Test coverage gap: no test exercises issue recording or naming across the real non-main-thread bridge

- **File**: `Tests/SnapshotsUnitTests/ExpectSnapshot/FailureReportingTests.swift:6`
- **Failure scenario**: The failure-reporting tests (`FailureReportingTests`, `AsserterTests`) are `@MainActor` and inject the `recordIssue` closure (`Asserter.swift:54`), so they bypass both the `DispatchQueue.main.sync` hop and the production `Issue.record`/`Test.current` branch — the exact code paths findings 1-3 fall through. There is no test that (a) triggers a snapshot failure from a non-`@MainActor` test and asserts the issue is attributed to that test (e.g. via `withKnownIssue` matching, which would fail today), (b) runs two same-named assertions from two tests/child tasks and asserts distinct deterministic reference paths, or (c) covers the precondition failure mode. The repetition suite exercises repetition only in an Xcode-hosted plan, not under `swift test`.
- **Evidence**: `FailureReportingTests.swift:6-34` and `AsserterTests.swift:6-48` both construct `IssueRecordingAsserter` with an injected `recordIssue` closure on `MainActor`; `rg 'withKnownIssue' Tests/` has no hits in the ExpectSnapshot integration tests; the only `Task.detached` test (`SnapshotExecutionContextOwnershipTests.swift:34-45`) checks task-local inheritance, not issue attribution or naming.
- **Suggested fix**: Add an integration test in a non-`@MainActor` suite that wraps a deliberately mismatching `#expectSnapshot` in `withKnownIssue` and asserts the issue is matched (this fails until finding 1 is fixed and then guards the regression); add a naming test that runs the same named assertion from two tests/child tasks and asserts stable file paths; add an exit-test (`#expect(processExitsWith:)`) for the precondition if the trap is kept.
- **needs_dynamic_verification**: false
