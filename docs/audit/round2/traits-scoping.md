# Audit round 2: traits-scoping

Lane traits-scoping, round 2. The recursion fix (isRecursive=true + per-case token guard + idempotent withAttemptScope) is architecturally sound: swift-testing receives a recursive `__TestScopingBox` via the `__SuiteTraitBox(trait).wrapped` compile-time coercion (SnapshotSuite.swift:126), and suite/test and nested-suite value precedence is correct-by-construction (theme/record/sizes/difftool/strategy overwrite their task-local; padding/backgroundColor ASSIGN their decorator field), so double/recursive application is idempotent and cannot accumulate — refuting the "padding doubles to 2P" hypothesis. Round-1 findings 1-5 are present and coherent. Four items survive: (1) MEDIUM — parameterized `@Test(arguments:)` with unnamed/non-argument `#expectSnapshot` now collides on one reference file because per-case fresh contexts restart the `.N` counter at 1 while the reference name never folds in the `Test.Case` identity; this is round-1 finding 1's second half left unimplemented, turned by the recursion change from racy-distinct into a deterministic collision (needs dynamic verification). (2) LOW — a residual box-init ambiguity for a `SnapshotTrait & Testing.SuiteTrait & SnapshotTestScoping` (non-marker) shape (inits 3 vs 4 incomparable), unreachable through the public macros which constrain to the marker protocols, compile-time only. (3) IMPROVEMENT — suite-vs-test and nested-suite same-trait precedence is validated only by self-consistent image comparison, which cannot detect a precedence inversion; round-1 finding 6 coverage gap remains open. (4) IMPROVEMENT — the `.record(false)` -> `.never` divergence is intentional, well-documented (Traits.md/MIGRATION.md), and confirmed not auto-triggered by the migration CLI; flagged for explicit sign-off. No precedence-regression BUG found — the empirical integration references (rebaselined post-fix, CI green) plus swift-testing's ancestor-prepend ordering indicate test-over-suite precedence holds; the risk is that no inverting-capable test guards it.

## Findings (severity order)

### 1. Parameterized `@Test(arguments:)` + unnamed `#expectSnapshot` collide on one reference file (round-1 finding 1's Test.Case-identity half left unimplemented)
- **Severity:** medium
- **File:** Sources/SnapshotTestingMacros/Assertion/Asserter.swift:163
- **Failure scenario:** A `@Test(arguments: [...])` parameterized test makes one UNNAMED, NON-`argument:` `#expectSnapshot(view)` call whose render differs per argument case. Each case gets a fresh `SnapshotExecutionContext` (per-case token binding), which restarts pointfree's `.N` reference identifier at `.1`. But the reference name/directory folds in only `#function` and the assertion's own `argument:` — never the `Test.Case` parameterization identity. All N cases resolve the identical reference file (e.g. `render_light.1.png`): cases that render differently overwrite each other on record and fail against each other on verify; cases that happen to render identically pass deceptively against a single shared reference.
- **Evidence:** `SnapshotTestScoping.swift:30-38` binds a per-case token via `withAttemptScope` (fresh token when current==nil, `SnapshotAttemptToken.swift:47-55`) → each parameterized case = distinct `Test.Case` = distinct `provideScope(testCase!=nil)` invocation = fresh context, `.N` from 1 (`SnapshotAttemptToken.swift:30-40`). `Asserter.swift:144-164`: `referenceIdentifier` keys the counter on `directoryUrl + request.testName`. `NameAssertionRequestGenerator.swift:54-63`: `testName = [configurationName, context.name, size, theme]` — no `Test.Case`. `ExpectSnapshotAdapter.swift:70-78`: `configurationName = configuration.name ?? DerivedSnapshotNames.argumentName(from: configuration.value)` — i.e. the assertion's own `argument:`, not the `@Test` parameterization. grep confirms `Test.Case.current` appears only in comments across the name/dir derivation path; base name flows from `function: #function` (`expectSnapshot.swift:8`), lexically identical across argument cases.
- **Suggested fix:** When `Test.Case.current` indicates a parameterized case, fold its identity (argument label/index or case display name) into `request.testName` and the counter key so each case gets a distinct reference file; or emit a diagnostic requiring `named:`/`argument:` disambiguation for unnamed `#expectSnapshot` inside `@Test(arguments:)`.
- **needs_dynamic_verification:** true

### 2. Residual `__SuiteTraitBox`/`__TestTraitBox` init ambiguity for a `SnapshotTrait & Testing.SuiteTrait & SnapshotTestScoping` (non-marker) shape
- **Severity:** low
- **File:** Sources/SnapshotTestingMacros/Traits/_Types/SnapshotTrait/__SuiteTraitBox.swift:29
- **Failure scenario:** A custom trait conforming to the package's `SnapshotTrait` base AND `Testing.SuiteTrait` directly AND `SnapshotTestScoping`, but NOT the `SnapshotSuiteTrait` marker, excludes init 5 and leaves inits 3 and 4 maximal-but-incomparable (`Testing.SuiteTrait` does not refine `SnapshotTrait` and vice-versa) → "ambiguous use of init" in generated code, the same bug class round-1 finding 5 closed, one layer down. Identical residual gap exists in `__TestTraitBox` (init 3 vs init 4).
- **Evidence:** `SnapshotSuiteTrait.swift:7` defines `SnapshotSuiteTrait: SnapshotTrait, Testing.SuiteTrait`, so package traits (`RecordSnapshotTrait` etc.) resolve to the unique most-specific init 5 — unambiguous. `TraitBoxTests.swift`'s `DualConformingTrait` omits `SnapshotTrait` → resolves to init 3, so no existing type triggers it. Reachability: UNREACHABLE via the public macros — `@SnapshotSuite(_ traits: any SnapshotSuiteTrait...)` (`SnapshotSuiteMacroDefinition.swift:71-73`) and `@SnapshotTest(_ traits: any SnapshotTestTrait...)` (`SnapshotTestMacroDefinition.swift:82-83`) constrain inputs to the marker protocols, and any marker-conforming trait resolves to init 5. Only a direct `__SuiteTraitBox(custom)` call (public-but-"do not use" type) with the exact non-marker shape hits it; it is a compile-time error, not a runtime defect.
- **Suggested fix:** Either add a disambiguating `init(_ trait: any Testing.SuiteTrait & SnapshotTrait & SnapshotTestScoping)` to both boxes, or extend the `DualConformingTrait` regression to also conform to `SnapshotTrait` so the gap is covered, or document that custom traits must adopt the `SnapshotSuiteTrait`/`SnapshotTestTrait` marker protocols.
- **needs_dynamic_verification:** true

### 3. Suite-vs-test and nested-suite same-trait precedence only validated by self-consistent image comparison, not a value assertion (round-1 finding 6 still open)
- **Severity:** improvement
- **File:** Tests/SnapshotsUnitTests/ExpectSnapshot/SnapshotExecutionContextAttemptScopingTests.swift:44
- **Failure scenario:** The recursion change reorders when/where trait scopes bind, making precedence direction load-bearing. The only coverage that test-level overrides suite-level (and later-duplicate-wins) is `ExpectSnapshot+Traits.swift` — UIKit-gated, image-comparison. Image comparison passes as long as rendering is SELF-CONSISTENT: if precedence silently inverted (suite value winning over test), re-recording would produce a matching WRONG reference and the test would stay green. It therefore cannot catch a precedence inversion, only rendering instability. Nested suite-vs-suite precedence on the same trait type (e.g. `@Suite(.theme(.light))` enclosing `@Suite(.theme(.dark))`) — whose correctness depends on swift-testing's ancestor-recursive-trait ordering — is entirely untested; the `Nested` case only exercises a test's own duplicate traits under a single suite level. No direct unit/integration assertion checks that `ThemeSnapshotTrait.current` (or Record/Sizes/DiffTool/Strategy) reflects the expected winner inside the scope.
- **Evidence:** `SnapshotExecutionContextAttemptScopingTests.swift` covers only attempt/token scoping, not cross-trait precedence. `ExpectSnapshot+Traits.swift:12-42` asserts precedence solely through committed images (references rebaselined post-fix in `ee0b08f`, so a same-file green proves only consistency). Precedence is very likely correct (swift-testing prepends ancestor recursive traits so outer=suite, inner=test; task-local inner-wins; CI green) but no inverting-capable test exists.
- **Suggested fix:** Add direct-value precedence unit tests: assert the task-local inside the scope for `@Suite(.record(.missing))+@Test(.record(.never))` (test wins) and nested `@Suite(.theme(.light))` / `@Suite(.theme(.dark))` (inner suite wins), plus a decorator-merge assertion across suite+test scopes.
- **needs_dynamic_verification:** false

### 4. `.record(false)` -> `.never` divergence is intentional, well-documented, and not auto-triggered by migration — confirm senior sign-off
- **Severity:** improvement
- **File:** Sources/SnapshotTestingMacros/Traits/PointfreeSnapshotTesting/RecordSnapshotTrait+Init.swift:30
- **Failure scenario:** N/A — not a bug. Round-1 finding 4 was resolved by DOCUMENTING (not changing) the divergence: `.record(false)` maps to `.never` ("verified": a missing reference is a hard failure) rather than pointfree's `false` -> `.missing`. This is a deliberate product decision, flagged here for explicit sign-off. It is contained: the migration rewriter does NOT map the `record:` argument, so migrated code never lands on `.never` automatically — users reach the divergence only via manual rewrite, where the documented callout applies.
- **Evidence:** `RecordSnapshotTrait+Init.swift:9-17` (doc) and `:30-32` (`record ? .all : .never`); documented in `Documentation/Traits.md:72-75` and `MIGRATION.md:25-30` with `.record(.missing)` called out as the parity path. grep of `Sources/SnapshotMigrationSupport` shows no `.record(` emission (only incidental "record" in comments), confirming migration does not auto-translate `record: false`.
- **Suggested fix:** No code change. Record explicit sign-off that keeping the divergence (vs pointfree parity) is intended. Optionally, add a migration diagnostic/note when a `record: false` call site is rewritten, so manual migrators are pointed at `.record(.missing)`.
- **needs_dynamic_verification:** false
