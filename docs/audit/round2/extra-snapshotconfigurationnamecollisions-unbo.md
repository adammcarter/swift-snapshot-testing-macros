# Audit round 2: SnapshotConfigurationNameCollisions unbounded dictionary growth (lifetime, not thread-safety)

SUMMARY: Escalation largely refuted; round-2's improvement grade stands. SnapshotConfigurationNameCollisions.shared.valueDescriptionsByKey is the sole remaining process-lifetime insert-only structure (the holistic-#10 task-pointer context cache is genuinely gone; per-attempt contexts are freed with SnapshotAttemptToken). It is never cleared and — importantly — SHOULDN'T be: process-global scope is load-bearing for cross-test shared-helper collision detection (file header lines 16-18), and the occurrence dimension in the key is load-bearing for suppressing within-attempt false positives. Growth is O(distinct derived-name snapshots) in all normal usage (parameterized cases, retries/repetitions do not grow it), reclaimed at process exit; only a contrived single-attempt loop snapshotting identical values inflates it, still bounded by loop count. No crash, no correctness failure — improvement/low, not a prod blocker. I sharpened round-2 finding #4's bound (it omitted the occurrence multiplier) and, most usefully, REFUTED both of its suggested fixes: 'clear per test-run' breaks cross-test helper detection, and 'drop occurrence from key' introduces within-attempt false-positive collisions. The only safe hardening is capping the stored valueDescription length to bound per-entry memory. No tracked files were modified; conclusion is pure static reasoning (no dynamic probe required).

## Finding

**Title:** SnapshotConfigurationNameCollisions.shared is a process-lifetime insert-only registry — real but bounded (O(distinct derived-name snapshots)), NOT a prod-blocking leak; round-2's grade holds and its two suggested fixes are unsafe

**Severity:** improvement

**File:** Sources/SnapshotTestingMacros/Assertion/SnapshotConfigurationNameCollisions.swift:28

**Description:**

CANDIDATE LARGELY REFUTED / SEVERITY CONFIRMED AT IMPROVEMENT. The escalation asks whether the `.shared` singleton's dictionary is ever cleared or scoped across a large run. Answer: it is never cleared — `static let shared` (line 25) holds `valueDescriptionsByKey` (line 28), entries are inserted on first sight under the lock (lines 42-44) and nothing anywhere removes them (no removeValue/removeAll in the file or its only caller). After the round-1 fixes this is the SOLE process-lifetime accumulating structure in the assertion path: the old task-pointer context cache flagged by holistic #10 / round-1 concurrency #5 is genuinely deleted (TaskLocalSnapshotExecutionContext.swift:41-57 keeps no global cache), and each attempt's SnapshotExecutionContext — which owns the mutable occurrenceCounts/referenceCounts/usedNames dictionaries — is held on the per-attempt SnapshotAttemptToken (SnapshotAttemptToken.swift:20-21,27,30-40) and freed when the attempt's task-local scope ends. So only this registry survives to process exit.

GROWTH BOUND (sharpening round-2 finding #4, which slightly understated it). Round-2 characterized the bound as "distinct callSite x derivedName pairs = distinct references". That OMITS the occurrence dimension: the key is `callSite|occurrence|derivedName` (line 39), where occurrence comes from context.nextOccurrenceIndex (ExpectSnapshotAdapter.swift:765; SnapshotExecutionContext.swift:78-84) and counts repeats of one (callSite,derivedName) WITHIN a single attempt. So the true bound is (distinct derived names) x (max within-attempt occurrence per name). In all normal usage — parameterized @Test(arguments:) cases, or an in-test loop over DISTINCT values — occurrence stays 1 and growth is exactly O(distinct references), retained until process exit and reclaimed at exit. Repetitions/retries do NOT grow it (fresh attempt restarts occurrence at 1 and re-hits the same keys as a value-equal no-op, lines 42-47). The occurrence>1 multiplier bites ONLY a loop that snapshots the SAME derived name repeatedly in one attempt (i.e. snapshotting identical values in a loop) — contrived, and still bounded by the loop count. Per-entry cost is dominated by the stored valueDescription = String(describing: value), which can be KBs for rich models.

HONEST IMPACT: no crash, no correctness failure, no unbounded-per-iteration growth in realistic use. Footprint is single-digit MB for thousands of snapshots; only an extreme suite (100k+ derived-name assertions) or a long-lived host process running many bundles without restart reaches tens-to-hundreds of MB. This is improvement/low grade, matching round-2 finding #4 — I could not escalate it to a genuine leak.

**Evidence:**

SnapshotConfigurationNameCollisions.swift:24-49 — `static let shared` (25); `private var valueDescriptionsByKey = [String:String]()` (28); key `"\(callSite)|\(occurrence)|\(derivedName)"` (39); insert-on-first-sight then value-equality compare, never removed (41-47). grep over Sources: only 3 references to the type (def 24-25, 33) + one call site — no removeValue/removeAll/clear exists. ExpectSnapshotAdapter.swift:765 `occurrence = context.nextOccurrenceIndex(forKey:"\(callSite)|\(derivedName)")`, :767 conflictingValueDescription(...). SnapshotExecutionContext.swift:78-84 occurrenceCounts increments per (callSite|derivedName) within the attempt; :6-7 those counters are INSTANCE members, not global. SnapshotAttemptToken.swift:20-21 doc "context is stored on the token itself, so its lifetime is exactly the attempt's: there is no global cache to evict or leak", :27,:30-40 context held on token. TaskLocalSnapshotExecutionContext.swift:41-57 "Contexts are deliberately never cached here" — confirms the old process-global context cache is removed. Sole-survivor cross-check: rg for `static (let|var) shared`/global mutable dictionaries in Sources/SnapshotTestingMacros returns only this registry; other `static var current` are @TaskLocal scalar trait defaults, not accumulators.

**Suggested fix:**

Leave the process-global lifetime AS-IS — do NOT implement round-2 finding #4's "clear the registry per test-run via a scope hook": that would break the load-bearing cross-test detection documented in this file's header (lines 16-18) — the registry is process-global precisely so a shared helper invoked from several tests (same #function/file/line callSite) still catches when two callers' values fold to one reference name (the collision confirmed by concurrency round-2 finding #2). Also do NOT "drop occurrence from the key" to kill the loop growth: occurrence-in-key is what suppresses a legitimate WITHIN-attempt false positive — two distinct values in one attempt that normalize to one name are already disambiguated downstream by display-name dedup (SnapshotExecutionContext.swift:20-37, "-2"/"-3") and the per-attempt .N reference counter (:63-69), so they do not actually collide and must not be flagged; keying by callSite|derivedName alone would wrongly flag them. The only safe, optional hardening: cap/truncate the STORED valueDescription (e.g. to ~256 chars, enough to keep the diagnostic message useful) so a suite that snapshots large values doesn't retain MBs of describe-strings for the process lifetime. This bounds per-entry cost without changing entry count or detection semantics. Entry-count growth (O(distinct references)) is inherent to the feature and acceptable for an ephemeral test process.
