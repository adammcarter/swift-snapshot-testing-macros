# Audit round 2: renderer-view-generator

Verified all 7 round-1 findings for this lane are genuinely fixed in current source and tests: `backgroundColor` setter now opts into layer-backing; the new `AppKitImageRenderer` does offscreen-window re-hosting with appearance and scale handling; `recursiveDescription` applies size/theme; the availability check names macOS 13.0; `SnapshotInjectedViewController` vends via `loadView`; `AppKitImageRenderingTests` pixel-samples the renderer output. The new AppKit offscreen-window render path is sound for `draw(_:)`-based content — window lifecycle does not leak, scale handling (`bitmap = size × displayScale`) is correct and test-verified, appearance is applied before layout and dynamic colours resolve per theme, and layout timing is fine for non-layer content. Four items surfaced in this round, none critical or high.

## 1. MEDIUM — `preserveFrameBasedSize` guard `constraints.isEmpty` misclassifies frame-based roots that hold internal Auto Layout constraints, silently reintroducing the round-1 #2 collapse

- **File**: `Sources/SnapshotTestingMacros/_Convenience/SnapshotView+wrappingInContainerView.swift:58`
- **Failure scenario**: A frame-based root view sized externally by `frame` but laying its own subviews out internally with Auto Layout (a common migration shape from `assertSnapshot(of: view, as: .image)`) is skipped by this guard because `childView.constraints` is non-empty (it includes any constraint whose nearest-common-ancestor is childView, including constraints between two of its own subviews — not just prior frame pins). The frame pin never applies, `embedChild` forces `translatesAutoresizingMaskIntoConstraints = false` and edge-pins to the measuring container, and the view compresses to 0×0 or its intrinsic content size instead of its real frame size. Under `.minimum` + `.padding` this records a padding-only reference silently (green forever); without padding it throws `SizeError.zeroSize`.
- **Evidence**: Guard at line 58 checks ALL of `childView.constraints`; doc comment at lines 42-56 conflates "no constraints of its own" with "frame-based." Concrete repro: a `Card: NSView` sized `300×200` in `init`, with one Auto-Layout-centered 10×10 subview. `Card.constraints == [centerX, centerY]` (both owned by Card as common ancestor) → non-empty → guard returns early at line 58-60 without pinning 300×200. `FrameBasedViewSizingTests` only covers a plain no-subview `FillView` (empty constraints → pin applies) and a view with its own width/height constraints (skip correct there) — the mixed shape is uncovered.
- **Suggested fix**: Decide frame preservation from the view's own size signals, not from whether it holds any constraints at all. Options: (a) tag the pins with a known constraint identifier and only skip when that identifier's pin is already present; (b) after a trial layout, fall back to the frame pin only when compressed size comes back zero in a dimension the frame supplies; (c) restrict the guard to constraints that actually constrain `childView`'s own width/height (firstItem/secondItem == childView with a width/height attribute). Add a `FrameBasedViewSizingTests` case for a frame-based root with a centered non-size-driving subview, both bare and padded.
- **needs_dynamic_verification**: true

## 2. IMPROVEMENT — No test renders SwiftUI/`NSHostingController` content through `AppKitImageRenderer.cacheDisplay` — the dominant macOS path is unverified

- **File**: `Sources/SnapshotTestingMacros/Assertion/RequestGenerator/Generators/AppKitImageRenderer.swift:147`
- **Failure scenario**: `drawImage()` captures via `NSView.cacheDisplay(in:to:)`, which reliably captures `draw(_:)`-based content but is historically fragile against Core-Animation-hosted layer trees — exactly what `NSHostingView` (every `NSHostingController`'s view) produces for SwiftUI text, shapes, images, and materials. On macOS a SwiftUI `#expectSnapshot` funnels through this exact renderer, yet no test in the repo exercises an `NSHostingController` render. Compounding risk: the offscreen window is created with `defer: true` (no backing store until shown) and layout only calls `layoutSubtreeIfNeeded`, never `displayIfNeeded`/a CATransaction flush, so a SwiftUI layer tree may not have committed content when `cacheDisplay` reads it.
- **Evidence**: `AppKitImageRenderer.swift:147` `view.cacheDisplay(in: view.bounds, to: bitmap)`; window built with `defer: true` at line 51; `layOutHierarchy` (lines 108-115) calls only `layoutSubtreeIfNeeded`. `rg 'HostingController|HostingView' Tests/` returns only iOS integration reference dumps and macro-expansion fixtures — zero NSHostingController render paths in AppKit tests. `AppKitImageRenderingTests`/`ExpectSnapshotAppKitRuntimeTests` fixtures are all `draw(_:)`-based or plain `NSTextField`/`NSView`.
- **Suggested fix**: Add a main-actor test rendering `NSHostingController(rootView: Color(nsColor: .red).frame(width: 40, height: 40))` (or similar) through the AppKit image strategy and pixel-sample the bitmap centre. If `cacheDisplay` returns blank/partial content, switch capture to render the presentation layer explicitly (`layer?.render(in:)` after `displayIfNeeded`) before shipping AppKit SwiftUI support. Treat as a macOS release gate.
- **needs_dynamic_verification**: true

## 3. LOW — `AppKitImageRenderer` and `embedChild` leave the caller's view permanently mutated after a render (TAMIC, appearance, wantsLayer/background not restored)

- **File**: `Sources/SnapshotTestingMacros/Assertion/RequestGenerator/Generators/AppKitImageRenderer.swift:39`
- **Failure scenario**: `render()`'s teardown restores only superview, autoresizingMask, and frame (lines 39-41) — not `view.appearance` (set line 31) nor the `wantsLayer`/layer background written by `apply()` (line 34). Separately, `embedChild` (`SnapshotView+wrappingInContainerView.swift:26`) sets `translatesAutoresizingMaskIntoConstraints = false` on the caller's payload view during `.minimum` measurement and never restores it. This is the "restore mutation" sub-point of round-1 #2's suggested fix, which was never applied. Does not cause cross-render incorrectness within a fan-out (each render re-applies its own state), so impact is confined to reusing the exact snapshotted view instance afterward in a real layout.
- **Evidence**: `AppKitImageRenderer.swift:26-44` captures/restores only `initialFrame`/`initialAutoresizingMask` plus `removeFromSuperview`; no restore for `appearance` (line 31) or `wantsLayer`/background (lines 98-106, invoked line 34). `SnapshotView+wrappingInContainerView.swift:26` sets TAMIC unconditionally with no save/restore anywhere in `embedChild`.
- **Suggested fix**: Snapshot and restore `view.appearance` and `view.wantsLayer` alongside frame/autoresizingMask in `render()` (or apply appearance/background to a throwaway wrapper). In `embedChild`, capture and restore the child's original TAMIC, or measure on a copy/wrapper.
- **needs_dynamic_verification**: false

## 4. IMPROVEMENT — `host()` activates fresh window-edge constraints on every render without an explicit deactivate — correct today only via ARC teardown

- **File**: `Sources/SnapshotTestingMacros/Assertion/RequestGenerator/Generators/AppKitImageRenderer.swift:83`
- **Failure scenario**: In the Auto Layout branch, `host()` activates fresh leading/trailing/top/bottom constraints against the new window's `contentView` on every `render()` call. The multi-size fan-out shares one `SnapshotViewController` across N size requests, so the same view is hosted N times, with nothing explicitly deactivating the prior render's constraints before re-hosting. Traced and confirmed NOT a live leak: those constraints are owned by the prior window's `contentView`, `host()` calls `view.removeFromSuperview()` first (line 75) which detaches cross-hierarchy constraints, and the whole prior `NSWindow` subtree is released at end of scope (`isReleasedWhenClosed = false` but never shown, no surviving reference). The invariant holds today, but only via ARC teardown timing and `removeFromSuperview` semantics rather than an explicit deactivate.
- **Evidence**: `AppKitImageRenderer.swift:78-89` host() Auto Layout branch activates constraints against `contentView` with no prior deactivate; `removeFromSuperview()` at lines 75 and 39; window is a local `let` (line 30) with `isReleasedWhenClosed = false` (line 54), never `close()`d/ordered on screen, deallocates at end of scope.
- **Suggested fix**: Make the invariant explicit for robustness — capture the activated constraints and `NSLayoutConstraint.deactivate` them in teardown alongside `removeFromSuperview`, or add a comment documenting that `removeFromSuperview` + per-render window disposal is what guarantees no stale window constraint reaches the next render of a shared controller.
- **needs_dynamic_verification**: false
