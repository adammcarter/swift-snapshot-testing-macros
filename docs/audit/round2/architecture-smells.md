## Findings

### 1. [improvement] `SnapshotMigrationRewriter` is a ~1180-line god-struct mixing edit-orchestration, string-template body rendering, and configurations analysis in one 1726-line file

- **File**: `Sources/SnapshotMigrationSupport/Rewriting/SnapshotMigrationRewriter.swift:66`
- **Failure scenario**: not a live bug — a maintainability/future-bug-surface risk. Both round-1 HIGH bugs (holistic.md #1 argument-destroying `@Suite` dedup, #2 `.init`/`SnapshotConfiguration` corruption) originated in this single type's string-manipulation methods. The specific bug-producing blind string passes are gone (replaced with AST-scoped rewriting), but the struct still spans lines 66-1248 (~40 private methods) mixing: (a) edit orchestration (`rewrite`/`rewriteNonParameterizedFunction`/`rewriteParameterizedFunction`/`apply`/`makeReason`/`index`); (b) body synthesis via multiline string templates plus manual comment+indentation reconstruction (`rewriteDirectBody`, `rewriteSwiftUI/DirectConfigurations/ConfigurationValuesBody`, `renderStatements`, `renderMultiline`, `normalizedLines`, `leadingCommentLines`, `baseIndentation`, `statementIndentation`, `configuration*Line`, `removingIndentation`, `trimmingTrailingWhitespace`); and (c) configurations-argument analysis (`rewriteConfigurationsArgumentsExpression` + the AST element rewriter + residual string heuristics).
- **Evidence**: struct declared at line 66, closing brace at 1248; file is 1726 lines. Responsibility clusters visible at: orchestration 69-486; body rendering 998-1168; configurations analysis 767-996; already-separated collector/parser types 1255-1726 (`RewriteCollector` 1255, `RewriteCollectorVisitor` 1274-1609, `LegacyFunction`/`FunctionParameterInfo`/... value types 1611-1667, `TopLevelReturnDetector` 1669-1726).
- **Suggested fix**: 1) zero-risk file split: move the already-private collector/visitor/model/detector types (1255-1726) to their own file(s), e.g. `RewriteCollector.swift`, `RewriteModel.swift`. 2) Extract a `LegacyBodyRenderer` value type owning cluster (b), taking `BodyRewriteParts` + indentation inputs and returning the rendered `{ ... }` string — this is the fragile hand-rolled-source area and deserves isolation + focused tests. 3) Extract a `ConfigurationsArgumentRewriter` owning cluster (c). Leaves `SnapshotMigrationRewriter` as thin orchestration (~300 lines). No behavior change.
- **needs_dynamic_verification**: false

### 2. [improvement] Configurations-argument path still analyses source as strings/regex despite the expression already being parsed to `ExprSyntax` nearby

- **File**: `Sources/SnapshotMigrationSupport/Rewriting/SnapshotMigrationRewriter.swift:928`
- **Failure scenario**: after `f1eeeab` migrated the *element initializer* rewrite to AST (`rewriteConfigurationElementInitializers` at 795, the correct verified fix for round-1 #2), the surrounding *decision* logic in the same path is still substring/regex based: `shouldAddConfigurationsTypeContext` (928-931) keys off `trimmed.contains("nil")`; `requiresUnsupportedArgumentNamingSkip` (956-980) keys off `.contains("name: nil")` / `.contains("SnapshotConfiguration(value:")`; `extractSnapshotConfigurationLiteralNames` (982-996) scrapes names with regex `name:\s*"([^"]*)"`; `invokeZeroArgumentFunctionReferenceIfNeeded` (917-926) + `sourceContainsZeroArgumentFunction` (946-954) use `\bfunc\s+NAME\s*\(\s*\)`. Most of these fail SAFE (over-skip, leaving the file untouched — conservative). The exception is `shouldAddConfigurationsTypeContext`: on any element whose value/name contains the literal substring "nil" (e.g. `name: "nil-state"`) it emits `(...) as [SnapshotConfiguration<T>]`. That coercion is benign for array-literal/`.map`-returning-Array arguments, but a forced `as` to `[SnapshotConfiguration<T>]` would fail to compile if a user's legacy `configurations:` expression is a non-Array `Collection` that also happens to contain "nil" — a narrow reported-as-migrated-but-non-compiling path in the same family as round-1 #2.
- **Evidence**: `rewriteConfigurationsArgumentsExpression` (767-783) chains the AST element rewrite then two string heuristics; `shouldAddConfigurationsTypeContext` returns `trimmed.contains("nil")` (930); `requiresUnsupportedArgumentNamingSkip` uses `.contains("name: nil")`/`.contains("SnapshotConfiguration(value:")` (969) and regex name extraction (983); `sourceContainsZeroArgumentFunction` regex (948). Old blind passes confirmed removed (`rg expandSnapshotConfigurationInitializerShorthand|addConfigurationInitializerTypeContext` -> not found).
- **Suggested fix**: reuse the parsed `ExprSyntax` already produced in `rewriteConfigurationElementInitializers` to drive all four decisions from syntax nodes (find an actual `NilLiteralExprSyntax` in value position, inspect real element arguments, inspect the callee) instead of substring/regex scans.
- **needs_dynamic_verification**: true

### 3. [improvement] `SnapshotConfigurationNameCollisions.shared` is an insert-only, never-evicted process-lifetime global; its doc covers thread-safety but not lifetime

- **File**: `Sources/SnapshotTestingMacros/Assertion/SnapshotConfigurationNameCollisions.swift:24`
- **Failure scenario**: this `@unchecked Sendable` box is backed by a `.shared` singleton with an unbounded dictionary: `valueDescriptionsByKey` is only ever written on the miss path (line 43) and there is no `removeValue`/`removeAll` anywhere in `Sources/.../Assertion` (confirmed by grep). Its doc comment (3-23) documents thread-safety (NSLock-guarded) but says nothing about lifetime. Growth is bounded by the number of distinct (callSite, occurrence, derivedName) triples — retries/repetitions re-register identical keys with identical descriptions and do not grow it — so this is slow growth with suite size (~one entry per parameterized case that derives a name), not a per-run leak. Same shape as holistic.md #10 (the `SnapshotExecutionContext` cache). Worth flagging because the sibling `SnapshotAttemptToken` doc explicitly claims "there is no global cache to evict or leak" (SnapshotAttemptToken.swift:20-21) while this global IS exactly an unevicted process-lifetime cache.
- **Evidence**: `static let shared` (25); `private var valueDescriptionsByKey = [String: String]()` (28), inserted at 43, never removed. Contrast `SnapshotAttemptToken.swift:20-21`.
- **Suggested fix**: add a lifetime note to the type doc, and consider scoping the registry to the attempt (bind it under `SnapshotAttemptToken` like the execution context) rather than a process-global singleton, so it releases when the attempt scope ends — matching the lifetime model the rest of the naming machinery already uses.
- **needs_dynamic_verification**: true

Minor dead-ish surface — a production method that exists solely to give one test a call site. (For contrast, the adjacent `configurationName(for:)` at 70 and `resolvedConfiguration(from:...)` at 750 are live production API, not dead.)
- **Evidence**: `displayName` body forwards to `SnapshotExecutionContext.resolvedAssertionName` (737-739); `rg '\.displayName\('` over Sources+Tests matches only `ExpectSnapshotAdapterTests.swift:13`; runtime naming uses `context.resolvedAssertionName` (`ExpectSnapshotAdapter.swift:1109`).
- **Suggested fix**: delete `ExpectSnapshotAdapter.displayName` and point the test directly at `SnapshotExecutionContext.resolvedAssertionName(named:baseName:)` (already internal and tested), or keep it only if a deliberate public naming API is intended (it currently is not — the enum is internal).
