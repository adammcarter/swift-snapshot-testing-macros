# Audit round 2: sizing-request-generators

Round-2 re-audit of lane sizing-request-generators (RequestGenerator/**, SizesSnapshotTrait family, fixed-size naming, slash-folder convention, zero/negative validation, sanitized dedup). Read the current source, the fix diffs (4e763ba, c43933f, 5549d90, 9c34c22, a297ebe, 94d11b6, bc5b934), the pinned pointfree 1.19.1 AssertSnapshot.swift, and all lane unit tests. Round-1 findings 1, 2, 3, 4, 6, 7 are solidly fixed and correctly wired: the `.N` counter is now attempt-scoped via `SnapshotExecutionContext` and the native path binds it (ExpectSnapshotAdapter:882/972/1087), dedup runs on the sanitized name, the slash convention is honored for configured tests without leaking raw `/`, AppKit scale/theme + `recursiveDescription` size/theme are applied at render time (with new passing unit tests), and non-positive/non-finite fixed lengths and scale now throw before measurement. One finding is an incomplete fix: the finding-5 dimension-embedding naming is not injective — fractional dimension + fractional scale values fold their decimal point to `-`, colliding with the `-{scale}x` suffix boundary, so two distinct valid sizes (e.g. `Size(.fixed(100), .fixed(2), scale: 5.5)` and `Size(.fixed(100), .fixed(2.5), scale: 5)`) produce the identical reference name and revert to positional-`.N` disambiguation, silently re-mapping geometry on sizes-list reorder — the exact harm finding 5 was meant to remove (narrow trigger, silent, medium). The remaining two are improvement-level: residual test-coverage gaps (no name-collision/order contract test, no AppKit render-scale pixel assertion, UIKit generator halves still macOS-gated, Set-based fan-out assertions) and a defensive note that the Asserter counter key uses the raw rather than sanitized testName (currently sound only because of an implicit upstream dedup + suffix-free-description invariant). No high-severity regressions found; no tracked files were modified and no builds/tests were run.

## Findings

### 1. Round-1 #5 fix is not injective: fractional dimension + fractional scale re-collide on testNameDescription, reintroducing order-dependent reference mapping

- **Severity:** medium
- **File:** `Sources/SnapshotTestingMacros/Traits/SizesSnapshotTrait+Size.swift:60`
- **Failure scenario:** The finding-5 fix (4e763ba) embeds concrete dimensions in the size name to make references "value-stable and order-independent" (asserted verbatim in `SizesSnapshotTraitSizeNamingTests`). It achieves this only for integral values. `lengthValueDescription` (lines 69-86) folds every non-word character to `-` via `\W+` regex, so a fractional value's decimal point becomes `-`. The scale suffix (line 60) is also introduced by a `-` (`-{scale}x`). When a dimension is fractional, its internal `-` becomes indistinguishable from the `-` that begins the scale suffix, so two genuinely different (width, height, scale) triples produce the identical `testNameDescription`. This is the exact failure mode finding 5 set out to eliminate: two distinct geometries in one test collapse to the same reference name and are disambiguated only by the positional `.N` counter (assigned in sizes-array x [.light, .dark] fan-out order). Reordering/editing the sizes list then silently re-maps each geometry to a different reference: false diffs in assert mode, silently re-recorded approvals in record mode, no way to tell from the file name which geometry a reference holds. Trigger is narrow (requires two fixed sizes in one test, at least one fractional value, and explicit scales whose `-` folding realigns), but every input is valid public API and the failure is completely silent. Because both colliding requests share one raw testName they share Asserter's counter key and get `.1`/`.2` rather than overwriting, so it manifests as the finding-5 order-fragility, not a hard overwrite.
- **Evidence:** Collision pair, both positive/finite (pass `validate()` at `SizeAssertionRequestGenerator.swift:148-160`): `Size(.fixed(100), .fixed(2), scale: 5.5)` -> description `fixed-100x2` (line 51) + scaleSuffix `-5-5x` (line 60, `lengthValueDescription(5.5)`=`5-5`) = `fixed-100x2-5-5x`. `Size(.fixed(100), .fixed(2.5), scale: 5)` -> description `fixed-100x2-5` (`lengthValueDescription(2.5)`=`2-5`) + scaleSuffix `-5x` = `fixed-100x2-5-5x`. Identical. These flow unchanged into `NameAssertionRequestGenerator.testName` (`NameAssertionRequestGenerator.swift:54-63`) -> identical raw `request.testName` -> identical Asserter counter key (`Asserter.swift:155-163`) -> `.1`/`.2` by fan-out order (`AccumulatedAssertionRequestGenerating` sequential loop). Integral-only names remain injective (`x` and structural `-` never appear inside integer strings), which is why the existing test `distinctFixedSizesInOneTestProduceDistinctNames` (`SizesSnapshotTraitSizeNamingTests.swift:57-66`) passes while missing this case.
- **Suggested fix:** Make the name grammar unambiguous: encode the decimal point with a word character (e.g. render `200.5` as `200p5`) instead of folding it to `-`, so the `-` separators that delimit width/height/scale fields can never be produced by a value. Alternatively fold the fraction to a token that survives pointfree's sanitize step and cannot occur as a field delimiter, or represent scale with a delimiter that a value can never emit. Add an injectivity unit test that includes a fractional-dimension + fractional-scale pair (e.g. the two sizes above) asserting distinct `testNameDescription`.
- **needs_dynamic_verification:** false

### 2. Coverage gaps remain from round-1 #8: no name-collision/order contract test, no AppKit render-scale assertion, UIKit generator halves still unit-untested

- **Severity:** improvement
- **File:** `Tests/SnapshotsUnitTests/Traits/SizesSnapshotTraitSizeNamingTests.swift:58`
- **Failure scenario:** The fixes closed most of finding 8, but concrete gaps persist. (a) No test exercises the `.1`/`.2` ordering contract for colliding size names, so the fractional collision above (and any future name-collision regression) is invisible to the suite; `distinctFixedSizesInOneTestProduceDistinctNames` only uses integral values plus one scale variant, which are inherently injective. (b) The AppKit finding-3 fix (scale actually applied to the raster in `AppKitImageRenderer.drawImage`, which sets pixel dimensions = size x displayScale) has no unit assertion on the produced NSImage's pixel dimensions - `StrategyAssertionRequestGeneratorTests` only checks `pathExtension == "png"`; `recursiveDescription` size/theme is well covered (`recursiveDescriptionLaysOutAtTheRequestSize` / `recursiveDescriptionAppliesThemeAppearance`) but the image render-scale is only exercised by integration snapshots. (c) Every generator unit test file is still `#if os(macOS)`, so `makeTraits()`, the UIKit `absoluteSize`/`compressedSizeWhenConstrained` branches, and `UIWindow` `windowScale` have no unit-level coverage. (d) The multi-size pipeline tests still assert with `Set(requests.map(\.testName))` rather than an ordered array, so a fan-out reordering would pass silently for any colliding-name case.
- **Evidence:** `SizesSnapshotTraitSizeNamingTests.swift:57-66` (integral-only distinctness check). `StrategyAssertionRequestGeneratorTests.swift:36-42` (image request only checks pathExtension, never pixel size). Set-based assertions: `AssertionRequestPipelineTests.swift:40` and `78`, `SizeAssertionRequestGeneratorTests.swift:40`, `ThemeAssertionRequestGeneratorTests.swift:18` and `31`. `#if os(macOS)` at line 1 of every RequestGenerator test file.
- **Suggested fix:** Add: an ordered-array assertion for a two-fixed-size fan-out including a deliberate name collision that documents the `.1`/`.2` order contract; an `AppKitImageRenderer` test asserting the rendered NSImage rep's `pixelsWide`/`pixelsHigh` equal size x displayScale (and 1x vs 2x differ); and mirror the generator unit tests into the iOS unit target so `makeTraits()`/UIKit sizing are exercised.
- **needs_dynamic_verification:** false

### 3. Defensive: Asserter counter key is the raw (unsanitized) testName while pointfree writes the sanitized testName; collision-safety leans on an implicit upstream invariant

- **Severity:** improvement
- **File:** `Sources/SnapshotTestingMacros/Assertion/Asserter.swift:163`
- **Failure scenario:** `referenceCounterKey` keys the per-attempt `.N` counter on directory + raw `request.testName`, but the reference file pointfree writes uses `sanitizePathComponent(testName)`. Two requests whose raw testNames differ but sanitize identically would therefore get independent counters (both `.1`) and collide on one file. Verified this is currently unreachable: the `SnapshotExecutionContext` dedup enforces uniqueness on the sanitized display-name component (`dedupKey` folds each `/`-segment through `folderComponent`, `SnapshotExecutionContext.swift:45-50`), and the size/theme description language is suffix-free (every size description carries a mandatory `fixed-`/`min-*` prefix and `x`/theme delimiters that a name cannot absorb across the `_` join), so no distinct deduped (name, size, theme) tuple collapses to another's sanitized testName. This is sound today but fragile: it is a non-obvious cross-file invariant, and any future addition of a new testName component, a new size-description form, or any caller that bypasses `resolvedAssertionName` would silently reintroduce the round-1 finding 1/2 collision class with no test guarding it. (Related trivial edge, also currently harmless: a single-segment trailing-slash name like `Menu/` returns nil from `NameAssertionRequestGenerator.normalizedPathName` (needs >=2 segments) and leaks the raw `/` into testName and the counter key; pointfree sanitizes it in the file name and the dedup prevents cross-collision, so impact is cosmetic.)
- **Evidence:** `Asserter.swift:155-163` builds the counter key from `request.testName` (raw, unsanitized). Pointfree file name uses `sanitizePathComponent(testName)`: `.build/checkouts/swift-snapshot-testing/Sources/SnapshotTesting/AssertSnapshot.swift:333-336`; with `named:` non-nil (our path) pointfree's own counter at line 328-330 is bypassed, so our key is the sole disambiguator. Dedup on sanitized name only: `SnapshotExecutionContext.swift:20-50`. Trailing-slash short-circuit: `NameAssertionRequestGenerator.swift:86-88`.
- **Suggested fix:** Sanitize the testName the same way pointfree does when composing `referenceCounterKey` (belt-and-suspenders so the counter groups exactly by the string that becomes the file name), and normalize the raw `/` out of the name for the <2-segment case. Add a regression test with two names that sanitize identically within one attempt, asserting distinct final reference files.
- **needs_dynamic_verification:** false
