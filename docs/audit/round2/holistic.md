### 1. CI Xcode version-matrix executes only 4 of ~40 unit suites; migration, trait, request-generator, failure-reporting, naming, config, AppKit-runtime and concurrency/attempt-scoping suites run on a single toolchain (26.3)
- **Severity:** improvement
- **File:** `.github/workflows/run-tests.yaml:48`
- **Failure scenario:** Round-1 finding #11, still open. `swift-build-matrix` runs `swift test --filter` for only `ExpectSnapshotAdapterTests`, `ExpectSnapshotMacroTests`, `SnapshotSuiteTests`, `SnapshotTestTests` across the Xcode 16.3-26.5 matrix (all four confirmed to be real, macOS-enabled `@Suite` types, so the matrix is not vacuous). Every other unit suite — all of `Tests/SnapshotsUnitTests/Migration/*` (12 files), `Assertion/RequestGenerator/*` (8), `Traits/*` (6), and the runtime `ExpectSnapshot` suites (AppKit rendering, failure reporting, naming, config, error policy, and the `SnapshotExecutionContext`/`ReferenceIdentifier` attempt-scoping suites) — executes on exactly one toolchain, 26.3, via the `macos-unit-tests` full-scheme job. The attempt-scoping/concurrency suites are precisely the areas most heavily reworked in the fix trains and are the most toolchain-sensitive, so single-toolchain execution is the top holistic release-readiness gap.
- **Evidence:** `run-tests.yaml:31-37` (matrix xcode list incl. 26.4/26.5 on macos-26); `:48-53` (the 4 `swift test --filter` invocations, the only executed tests in the matrix); `:115-138` (`macos-unit-tests` runs the full `SnapshotsUnitTests` scheme only on 26.3); `:140-162` (`native-consumer-build-checks` is `xcodebuild build-for-testing` only for 26.4/26.5). Migration/trait/request-generator suites confirmed present under `Tests/SnapshotsUnitTests/{Migration,Traits,Assertion/RequestGenerator}/*` but absent from every matrix filter. The 4 filter names map to real macOS-enabled `@Suite` types (`SnapshotTestTests.swift:3-20` is `#if os(macOS)` enabled / `#else .disabled`). NOTE: correcting round-1's overstatement (holistic.md:88) that 26.4/26.5 "never execute any test at all" — they were added to `swift-build-matrix.include` (lines 34-37) and DO now run the 4 filtered suites via `swift test`; what remains true is that the full unit/integration schemes are only build-for-testing on 26.4/26.5, and the ~36 non-filtered suites never run cross-toolchain.
- **Suggested fix:** Add the migration + concurrency/attempt-scoping suites to the matrix `--filter` list (they are host-independent macro/logic tests), and once a 26.4/26.5 test destination exists, promote at least `SnapshotsUnitTests` from build-for-testing to `test` on the newest rows. Alternatively run the full `SnapshotsUnitTests` scheme across the matrix instead of a hand-maintained filter list, which also removes the risk of new suites silently escaping cross-toolchain coverage.
- **needs_dynamic_verification:** false

### 2. SwiftLint analyzer rules (unused_declaration as error, unused_import) are configured but never executed — no lint gate runs `swiftlint analyze`
- **Severity:** improvement
- **File:** `.swiftlint.yml:28`
- **Failure scenario:** NEW. `.swiftlint.yml` declares `analyzer_rules: [unused_declaration, unused_import]` and escalates `unused_declaration` to `severity: error`, but `unused_declaration` and `unused_import` are SwiftLint *analyzer* rules that only run under `swiftlint analyze` (with a compiler log). The lint gate wired into `mise run lint` -> `Tools/format-check` and `Tools/format` both invoke `swiftlint` with the default `lint` subcommand, which silently skips all analyzer rules. Net effect: the project advertises (and a contributor reasonably assumes) that unused declarations/imports fail CI as errors, but they are never checked — dead code and unused imports pass the gate unnoticed.
- **Evidence:** `.swiftlint.yml:28-30` (`analyzer_rules:` list) and `:35-36` (`unused_declaration: severity: error`); `Tools/format-check:18-19` and `Tools/format:25-26,35-36` invoke `swiftlint --config ... --strict` (the default `lint` subcommand); `rg 'analyze' Tools/ mise.toml .github/` returns nothing — no gate ever runs `swiftlint analyze`.
- **Suggested fix:** Either add a `swiftlint analyze` invocation (with a compile-commands / compiler log) to the lint gate so the analyzer rules actually run, or move these two keys out of `analyzer_rules`/drop them so the config no longer implies enforcement that does not happen.
- **needs_dynamic_verification:** false

### 3. record-snapshots.yaml uploads every scheme's references in each per-scheme artifact and defeats its own `if-no-files-found: error` guard
- **Severity:** low
- **File:** `.github/workflows/record-snapshots.yaml:73`
- **Failure scenario:** NEW. The rebaseline workflow is now the "verification environment of record", but each matrix job deletes and re-records only its own `matrix.reference_paths`, then uploads `path: Tests/**/__Snapshots__/**` — every scheme's snapshot directories, not just the ones this job regenerated. So `recorded-references-SnapshotsUnitTests` bundles the freshly-recorded macOS unit refs together with the still-committed (un-regenerated) iOS integration refs, mislabeling the artifact and inviting a maintainer to commit stale cross-scheme references. It also defeats `if-no-files-found: error`: because the glob always matches the other schemes' committed PNGs, the guard can never fire even if THIS scheme recorded zero references (e.g. a scheme that rendered nothing), so a silently-empty record run still produces a green upload.
- **Evidence:** `record-snapshots.yaml:53-54` (`rm -rf ${{ matrix.reference_paths }}` deletes only this scheme's dirs); `:28-37` (per-scheme `reference_paths`); `:69-74` (`name: recorded-references-${{ matrix.scheme }}` but `path: Tests/**/__Snapshots__/**` with `if-no-files-found: error`).
- **Suggested fix:** Set `path: ${{ matrix.reference_paths }}` (or the scheme's `__Snapshots__` root) so each artifact contains only what that job actually recorded and `if-no-files-found: error` meaningfully catches an empty record run.
- **needs_dynamic_verification:** false

### 4. Tools/check-packages: `set -e` aborts on the `diff` exit status before the custom drift message and if/else, making the guidance branch dead code
- **Severity:** low
- **File:** `Tools/check-packages:7`
- **Failure scenario:** NEW. The manifest-sync gate runs `set -e` then a bare `diff` of the two Package manifests, then `if [ $? -eq 0 ]; then echo 'in sync' else echo 'Error: ...'; exit 1; fi`. Because `diff` is a simple command not in a conditional, `set -e` makes the script exit immediately with diff's status (1) whenever the manifests drift — the `if`/`else`, the explanatory "differ beyond the tools-version line" message, and the explicit `exit 1` are never reached. The gate still fails correctly (non-zero exit, so `mise run lint` fails on drift), so this is not a correctness hole; the only lost behaviour is the intended human-readable guidance, which a contributor who drifts the manifests will never see (they get a raw diff instead). The two manifests are currently byte-identical past line 1, so the gate is passing correctly today.
- **Evidence:** `Tools/check-packages:2` (`set -e`), `:7` (`diff <(tail -n +2 Package.swift) <(tail -n +2 Package@swift-6.2.swift)`), `:9-14` (`if [ $? -eq 0 ]` ... `else` ... `exit 1`) — lines 9-14 are unreachable on drift because line 7 triggers the `set -e` exit.
- **Suggested fix:** Guard the diff instead of relying on `$?` after `set -e`, e.g. `if diff <(...) <(...); then echo 'in sync'; else echo 'Error: manifests differ...'; exit 1; fi`.
- **needs_dynamic_verification:** false

### 5. Round-1 #12 residual: the expectParsesCleanly parse-clean assertion is applied in only 2 of 5 rewriter test suites
- **Severity:** improvement
- **File:** `Tests/SnapshotsUnitTests/Migration/SnapshotMigrationRewriterNamingParityTests.swift:1`
- **Failure scenario:** Round-1 #12's generic "output parses cleanly" helper WAS added (`MigrationOutputAssertions.swift` `expectParsesCleanly` does `Parser.parse` + `#expect(!tree.hasError)`) and is applied in `SnapshotMigrationRewriterCoreTests` (5 call sites) and `SnapshotMigrationRewriterParameterizedTests` (7) — exactly where round-1 #1/#2 lived, so the corruption-prone paths are covered. Residual gap: the other three rewriter suites — `NamingParityTests`, `CommentPreservationTests`, and `TerminalControlFlowTests` — have zero `expectParsesCleanly` calls, so their rewriter outputs (comment/trivia splicing and if/switch terminal-control-flow skips are both structural-corruption-prone) are not asserted to be syntactically valid Swift. This is a coverage residual only, not a defect; #12 is substantially closed.
- **Evidence:** `Tests/SnapshotsUnitTests/Migration/TestSupport/MigrationOutputAssertions.swift:6-16` (helper); per-file `expectParsesCleanly` counts: `CoreTests`=5, `ParameterizedTests`=7, `NamingParityTests`=0, `CommentPreservationTests`=0, `TerminalControlFlowTests`=0.
- **Suggested fix:** Call `expectParsesCleanly` on `result.output` in the NamingParity, CommentPreservation, and TerminalControlFlow rewriter test suites (or centralize it in the shared rewrite-assertion helper those suites already use) so every rewriter path is parse-checked.
- **needs_dynamic_verification:** false
