# Audit round 2: migration-cli

Audited the migration-cli lane (SnapshotMigrationSupport/**, SnapshotMigrationCLI) statically. The five round-1 holistic findings in this lane are genuinely and correctly fixed: ApplyLock's flock rewrite has no remaining unlink path and an idempotent guarded release; the staging `defer` in MigrationRunner correctly fires on every throw/early-return between staging creation and the defer; the `--help`/exit-code table matches the parser flags and `resolveExitCode`; the SwiftSyntax-scoped config rewrite correctly leaves receiver-qualified/nested `.init`, string contents, and lookalike types untouched; and the per-declaration counting model is well-covered. Five residual issues remain, all clustered on rewrite-shape coverage and report/exit accounting. MEDIUM (1): configuration `.init(...)` shorthands reachable only through control flow inside a `configurations:` `.map` closure (terminal if/switch expression, returns nested in guard/if/switch) escape the round-1 fix and are written as non-compiling code by `--apply` with no skip reason — the same silent-mis-migration failure mode round-1 #2 targeted, for a narrower input shape. LOW (2): a non-literal legacy `@SnapshotSuite` display name is mis-folded as a `@Suite` trait in the argument-carrying dedup path (type error); and `migratedDeclarations` is left non-zero on the migration-failure apply-skip path while the sibling apply-lock-failure path zeroes it, giving inconsistent JSON-report accounting for staged-but-unwritten work. IMPROVEMENT (2): a dead exit-code branch (hadMigrationFailures always implies failedDeclarations>0, so the `exitCode == .success` guard is unreachable); and a test-coverage gap for control flow inside config map closures plus the absence of any type-resolvability check on rewritten output. Compile-failure claims in finding #1 are marked needs_dynamic_verification (strong static reasoning, no build run per constraints).

## Findings

### 1. Configuration `.init(...)` shorthand inside control flow within a `.map` closure escapes rewriting, producing non-compiling applied output with no skip reason
- Severity: MEDIUM
- File: `Sources/SnapshotMigrationSupport/Rewriting/SnapshotMigrationRewriter.swift:862`
- Failure scenario: A `configurations:` argument built via `<seq>.map { ... }` where the element expression is reachable only through nested control flow — a terminal if/switch EXPRESSION whose branches are bare `.init(...)` (no `return`), or `return`s nested inside `guard-else`/`if`/`switch` — is not collected by `configurationElementExpressions` (846-882), which only handles direct `ReturnStmtSyntax` children (861-868) and `closure.statements.last` cast to `ExprSyntax` (869-873). The leftover `.init(...)` has no contextual element type (unlike an array literal, which round-1 HIGH #2 specifically targeted) and remains ambiguous. `rewriteConfigurationElementInitializers` returns the expression byte-identical when it finds no edits, so the declaration is still recorded `.migratable` with empty skip reasons (SnapshotMigrationRewriter.swift:147-154), counted as migrated, and written by `--apply` as non-compiling code.
- Evidence: `configurationElementExpressions` loop at 861-873 only matches `statement.item.as(ReturnStmtSyntax.self)` and `closure.statements.last...as(ExprSyntax.self)`; the main rewrite loop at 809-813 requires `element.as(FunctionCallExprSyntax.self)`, which a terminal `IfExprSyntax`/`SwitchExprSyntax` is not. Tests cover only simple map closures: `SnapshotMigrationRewriterParameterizedTests.swift:130` and `:476`. No test exercises control flow inside a config map closure; `SnapshotMigrationRewriterTerminalControlFlowTests.swift` covers control flow in the test body only.
- Suggested fix: Either recurse into nested control-flow bodies (guard/if/switch statements and if/switch expression branches) when collecting configuration-element `FunctionCallExpr` nodes, or detect a leftover bare `.init(` after the pass and emit an explicit skip reason (e.g. `unsupported-configuration-shape`) so the file is surfaced and left untouched. Add rewriter tests for terminal-if-expression, all-returns-in-switch, and guard+return map closures.
- needs_dynamic_verification: true

### 2. Non-literal legacy `@SnapshotSuite` display name is mis-folded as a `@Suite` trait, producing non-compiling output
- Severity: LOW
- File: `Sources/SnapshotMigrationSupport/Rewriting/SnapshotMigrationRewriter.swift:1450`
- Failure scenario: In the argument-carrying `@Suite` dedup/fold path (`removeDuplicateSuiteAttributeIfNeeded`, 1338-1388), `traitFoldingEdit` folds every non-first-position argument of the legacy `@SnapshotSuite` into the surviving `@Suite`, skipping the first argument only when `isDisplayNameArgument` is true. That check (1450-1452) recognizes only `StringLiteralExprSyntax`/`NilLiteralExprSyntax`. A non-literal display name — `@SnapshotSuite(Self.suiteName, .theme(.light))`, `@SnapshotSuite(Constants.name, ...)` — is a MemberAccessExpr/DeclReferenceExpr, is not recognized, and gets folded into `@Suite(...)` as if it were a trait. `@Suite`'s variadic expects `any SuiteTrait`, so the output fails to compile. Reported as migrated with no skip reason and written by `--apply`.
- Evidence: `isDisplayNameArgument` at 1450-1452 checks only string-literal/nil-literal kinds; fold loop at 1428-1434 appends `argument.expression.trimmedDescription` for any non-skipped argument. Triggered only for a partially-migrated declaration (pre-existing argument-carrying `@Suite` alongside `@SnapshotSuite`) with a non-literal legacy display name; the bare-`@Suite` rename path doesn't hit this.
- Suggested fix: Broaden the first-position display-name guard to treat the first `@SnapshotSuite` argument as a display name whenever the legacy overload places a `String`/`String?` there, rather than literal-only detection. Add a rewriter test with a non-literal legacy display name in the fold path.
- needs_dynamic_verification: false

### 3. Report inconsistency: `migratedDeclarations` counts staged-but-unapplied work on the migration-failure apply-skip path but is zeroed on the apply-lock-failure path
- Severity: LOW
- File: `Sources/SnapshotMigrationSupport/Runner/MigrationRunner.swift:201`
- Failure scenario: On apply-lock-acquisition failure the code deliberately moves the count to failed and zeroes it (`failedDeclarations += migratedDeclarations; migratedDeclarations = 0`, 214-215). But when `hadMigrationFailures` is true, the entire apply block is skipped by the guard at 201 (`options.mode == .apply && !hadMigrationFailures`), so `migratedDeclarations` retains the value accumulated at 195 even though `filesApplied == 0` and nothing touched disk. An `--apply` run blocked by one unparseable/failed-staging file emits a JSON report with e.g. `migratedDeclarations: 5, filesApplied: 0`, and `migrationPercentage` (275) reflects "successfully rewritten" rather than "applied". Exit code is still correctly non-zero via `failedDeclarations>0`, so this is a reporting-semantics discrepancy, not a wrong exit code.
- Evidence: Line 195 `migratedDeclarations += declarations.count`; guard 201 skips the apply block (including the 214-215 zeroing) when `hadMigrationFailures`; no post-block adjustment before the report is built (286) or percentage computed (275). Compare the lock-failure catch at 209-217 which zeroes it. Reachable: file A stages OK (migrated+=1, queued), file B rewrite throws (hadMigrationFailures=true, 119-120) → apply skipped → migrated=1, filesApplied=0.
- Suggested fix: Make the two apply-skipped paths agree — when the apply phase is skipped due to `hadMigrationFailures` in apply mode, move staged (pending) declaration counts to `failedDeclarations` and zero `migratedDeclarations` (mirroring 214-215), or add a distinct `stagedDeclarations`/`appliedDeclarations` field so consumers can distinguish rewritten-but-unapplied from applied.
- needs_dynamic_verification: false

### 4. Unreachable exit-code branch in runWithOutcome (hadMigrationFailures always implies a non-success exit code)
- Severity: IMPROVEMENT
- File: `Sources/SnapshotMigrationSupport/Runner/MigrationRunner.swift:308`
- Failure scenario: `if options.mode == .apply, hadMigrationFailures, exitCode == .success { exitCode = .migrationFailure }` (308-310) is dead code. Every site that sets `hadMigrationFailures = true` also increments `failedDeclarations` (119-120, 178-179), and there is no path that decrements it. Therefore whenever `hadMigrationFailures` is true, `failedDeclarations >= 1`, so `resolveExitCode` (MigrationReport.swift:70-82) returns `applySafetyFailure` or `migrationFailure` — never `.success`. Harmless (never fires) but obscures the actual invariant.
- Evidence: `hadMigrationFailures` set only at 119 (with `failedDeclarations+=1` at 120) and 178 (with `failedDeclarations+=max(1,count)` at 179). `failedDeclarations` is only ever incremented. `resolveExitCode` returns a failure code for `failedDeclarations>0` before ever reaching `.success`.
- Suggested fix: Remove the redundant branch, or keep it as defensive coupling with a comment stating the invariant (`hadMigrationFailures ⇒ failedDeclarations>0 ⇒ non-success`).
- needs_dynamic_verification: false

### 5. Coverage gap: no rewriter test exercises control flow inside a `configurations:` `.map` closure, nor validates type-resolvability of migrated output
- Severity: IMPROVEMENT
- File: `Tests/SnapshotsUnitTests/Migration/SnapshotMigrationRewriterParameterizedTests.swift:130`
- Failure scenario: The config-map rewrite is tested only for the two shapes it handles (simple implicit result at :130, single explicit `return` at :476). No test covers control flow inside a config map closure — exactly where finding #1's silent non-compiling output arises. `expectParsesCleanly` asserts only that output parses, not that it type-checks, so it cannot catch a leftover `.init(...)` that is syntactically valid but has no contextual base.
- Evidence: `SnapshotMigrationRewriterParameterizedTests.swift` map tests at :130 and :476 only; `SnapshotMigrationRewriterTerminalControlFlowTests.swift` covers control flow in the direct test body, never in a config-argument closure. `MigrationOutputAssertions.expectParsesCleanly` is a parse check, not a type check.
- Suggested fix: Add rewriter tests asserting that config map closures with (a) a terminal if/switch expression, (b) all returns nested in switch/if, and (c) a guard+return are either fully rewritten to `SnapshotConfiguration<T>(...)` or reported with an explicit skip reason. Pair with the finding-#1 fix so the tests encode the intended contract.
- needs_dynamic_verification: false
