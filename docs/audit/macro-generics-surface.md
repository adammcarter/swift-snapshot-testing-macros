# Audit findings: macro-generics-surface

Reviewed the `#expectSnapshot` macro and its 17-overload generic surface end to end: macro expansion (`ExpectSnapshotMacro`), the `__expectSnapshot` runtime overloads, `ExpectSnapshotAdapter`, `SnapshotConfiguration`/parser, name derivation, and the request-generator/asserter pipeline down into the vendored pointfree 1.19.1 source. The headline finding is that the `DispatchQueue.main.sync` hop inside `runOnMainActor` strips Swift Testing's `Test.current`, so real snapshot MISMATCHES (not thrown errors, which are correctly re-thrown and attributed) are recorded via `Issue.record` with no test context for every non-`@MainActor` test — the failing test can report PASS. Secondary findings cover lossy derived configuration names colliding under pointfree's process-global counter, a `@MainActor`-vs-hop fork in which counter instance is used (resurrecting the repetition-safety regression the dedicated test target exists to guard against), tuple naming baking in module/type qualification, non-closure-literal `makeValue` arguments being silently mis-classified or dropped, a trailing-line-comment trivia bug that corrupts macro expansion, and a hard `preconditionFailure` crash for foreseeable XCTest/detached-task misuse. Known bugs 1–6 (task-pointer cache reuse, AppKit appearance, migration rewriter non-compiling output, migration rewriter naming, scanner skip list, Swift 6.1 fixes) were not re-reported. Overload resolution across the 17 declarations (sync/throws/async/asyncThrows × tuple arities × parser overload set) checked out sound; the reader's escalations on `@unchecked Sendable` box safety and try/await macro effect plumbing were investigated and settled as currently safe.

## 1. Snapshot mismatches in non-@MainActor tests are recorded outside the test task, so the failing test can pass

- **Severity:** high
- **File:** `Sources/SnapshotTestingMacros/Assertion/ExpectSnapshotAdapter.swift:799`
- **Failure scenario:** `@Test func f() { #expectSnapshot(Text("x")) }` runs on Swift Testing's cooperative pool (not the main thread), so `runOnMainActor` takes the `DispatchQueue.main.sync` branch. Task-locals do not propagate into a dispatch work item, so inside that block `Test.current` is `nil`. If the reference image doesn't match, `IssueRecordingAsserter.assertSnapshot` catches the resulting `SnapshotError` and calls `Issue.record` right there, on the main-thread side, with no active test context. Swift Testing cannot attribute an issue recorded outside any test task to `f()` — it surfaces as an orphan/run-level issue at best, and `f()` itself reports PASS despite a real visual regression. Thrown machinery errors *are* re-thrown across the box and recorded test-side with correct attribution via `runOnMainActorRecordingIssues`, which shows the mismatch path is the odd one out.
- **Evidence:** `ExpectSnapshotAdapter.swift:787-813` (`if Thread.isMainThread ... else DispatchQueue.main.sync { ... }`) → `assertSnapshotSync` (`assertSnapshot.swift:10-14`) → `Asserter.assertSnapshotsSync` (`Asserter.swift:8-18`) → `IssueRecordingAsserter.assertSnapshot` (`Asserter.swift:56-88`) catches `SnapshotError` and records without rethrowing; `Asserter.swift:107` checks `Test.current != nil`, which is `nil` inside the dispatch block, so both branches call `Issue.record` outside any test context. Contrast with `runOnMainActorRecordingIssues` (`ExpectSnapshotAdapter.swift:754-780`), which records thrown errors on the test-task side with correct attribution. Swift Testing runs nonisolated tests on the cooperative pool, so `Thread.isMainThread` is false for every plain `@Test func` in this repo's own integration suites (e.g. `Tests/SnapshotsIntegrationTests/ExpectSnapshot/ExpectSnapshot+Closures.swift`, all nonisolated). `Tests/SnapshotsUnitTests/ExpectSnapshot/FailureReportingTests.swift:6,23` shows only an injected-closure, `@MainActor` unit test — the real off-main `Issue.record` path is never exercised.
- **Suggested fix:** Never record issues on the far side of the hop. Have `IssueRecordingAsserter` collect `SnapshotError`s (or make `assertSnapshotsSync` return failures) and surface them across the `SyncMainActorResultBox` so `runOnMainActorRecordingIssues` records them on the test task, as it already does for thrown errors. Add an integration test that forces a mismatch inside a nonisolated test and asserts the issue is attributed to that test (`withKnownIssue`).
- **needs_dynamic_verification:** true

## 2. Derived configuration names can collide across parameterised cases; identical testNames fall back to pointfree's execution-order counter, nondeterministically swapping reference files

- **Severity:** medium
- **File:** `Sources/SnapshotTestingMacros/Assertion/ExpectSnapshotAdapter.swift:143`
- **Failure scenario:** `argument:`/unnamed configuration names are derived via `String(describing: value)` folded through `SnapshotNameNormalizer` (`\W+` → `-`), which is lossy — e.g. `"v1.0"` and `"v1 0"` both normalize identically. Two `Test.Case`s of one `@Test(arguments:)` then produce the identical final testName (`<config>_<displayName>_<size>_<theme>`), because each case gets a fresh `SnapshotExecutionContext` with the bare function name as displayName. `Asserter.swift:149` passes `named: nil` to pointfree, so pointfree disambiguates identical testNames with a process-global per-(directory, testName) counter assigned by arrival order. Swift Testing executes parameterised cases in parallel, so arrival order varies run-to-run: case A intermittently compares against case B's reference — flaky mismatches or a silent wrong-reference pass, and swapped files on re-record. No collision diagnostic exists anywhere.
- **Evidence:** `ExpectSnapshotAdapter.swift:143-146` and `35-43` (argument/unnamed config → `DerivedSnapshotNames.argumentName`); `DerivedSnapshotNames.swift:2-5` → `SnapshotNameNormalizer.swift:4-8` (lossy fold); `NameAssertionRequestGenerator.swift:42-51` (testName composition); `Asserter.swift:149` (`named: nil`); vendored pointfree 1.19.1 `AssertSnapshot.swift:326-331`, `555-567`, `613-635` (counter keyed on directory+testName, per-process instance, never bound because the package doesn't use pointfree's `.snapshots` trait — the only binder is `SnapshotsTestTrait.swift:54`). Committed filenames all end `.1.png`, confirming the counter identifier path.
- **Suggested fix:** Pass a stable non-nil `named:` (e.g. `"1"`) to `verifySnapshot` so filenames never depend on the process-global counter, and detect collisions by keeping a per-context registry of resolved `configurationName + displayName` pairs, recording an `Issue` when two distinct configuration values resolve to the same artifact name.
- **needs_dynamic_verification:** true

## 3. Trailing line comment on the last macro argument corrupts the expansion

- **Severity:** medium
- **File:** `Sources/SnapshotsMacros/ExpectSnapshot/ExpectSnapshotMacro.swift:72`
- **Failure scenario:** The expansion is assembled by plain string concatenation and re-parsed with `ExprSyntax(stringLiteral:)`. Interpolating `\(value)` uses `SyntaxProtocol.description`, which includes trailing trivia. A same-line `//` comment after the final macro argument (no trailing comma, so the comment attaches to the expression's last token, not a comma token) is spliced directly before the template's `,`: `#expectSnapshot(Text("x") // hero variant\n)` expands to `... Text("x") // hero variant,\n  named: nil, ...` — the comma and rest of the line are commented out, the expansion fails to parse, and the user sees a cryptic "expected ','" error inside macro-expanded code for an innocent comment. Same applies to `named: "x" // note` as the last parenthesised argument before a trailing closure.
- **Evidence:** `ExpectSnapshotMacro.swift:62-72` (`leadingArguments = "  \(valueArgument),\n"` via `"\(value)"`), `:54` (`named` interpolated before `,` at line 77), `:86-88` (`ExprSyntax(stringLiteral:)` re-parse). SwiftSyntax attaches same-line trailing comments to the preceding token's trailing trivia; only `trimmedDescription`/`.trimmed` strips it — plain interpolation does not. No expansion test covers comment trivia (`Tests/SnapshotsUnitTests/ExpectSnapshot/ExpectSnapshotMacroTests.swift` covers clean shapes only).
- **Suggested fix:** Interpolate trimmed nodes (`\(value.trimmed)`, `\(named.trimmed)`, `\(closure.trimmed)`) or build the call with SwiftSyntaxBuilder instead of string concatenation. Add `assertMacro` cases with trailing line comments on the value, `named:`, and closure positions.
- **needs_dynamic_verification:** true

## 4. Non-closure-literal makeValue is silently mis-classified: code dropped from the expansion, confusing post-expansion compile error

- **Severity:** medium
- **File:** `Sources/SnapshotsMacros/ExpectSnapshot/ExpectSnapshotMacro.swift:22`
- **Failure scenario:** The macro classifies arguments purely structurally: only `ClosureExprSyntax` counts as a makeValue closure. The public macro declarations accept any expression of function type (`_ makeValue: @escaping () -> V`), so `#expectSnapshot(makeHeader)` (a function reference) or `let build = { Text("x") }; #expectSnapshot(build)` type-checks against the macro declaration, then the expansion treats the reference as the direct `value`, emitting `__expectSnapshot(makeHeader, named: ...)` with no `makeValue:` — no runtime overload accepts a function-typed `value` (`V` must conform to `View`), producing "no exact matches in call to global function '__expectSnapshot'" inside generated code with no macro diagnostic. Worse for two-argument shapes: `#expectSnapshot(configuration, buildFn)` passes the guard (`value = configuration`) and the non-literal `buildFn` is silently dropped from the emission entirely.
- **Evidence:** `ExpectSnapshotMacro.swift:13-16` (`compactMap` `.as(ClosureExprSyntax.self)`), `:17-28` (first unlabeled non-closure becomes `value`), `:36-41` (makeValueClosure only from closure literals), `:43` (guard passes because `value != nil`). Macro declarations accepting arbitrary function-typed expressions: `ExpectSnapshotMacroDefinition.swift:22-25, 74-78`. Runtime overloads in `expectSnapshot.swift:5-13` require `V: View` for the unlabeled first parameter, so the emitted call cannot resolve.
- **Suggested fix:** Treat any remaining unlabeled argument (after value/argument extraction) as the makeValue expression regardless of syntax kind and emit `makeValue: <expr>`; alternatively diagnose explicitly: "makeValue must be a closure literal". Add `assertMacro` coverage for function-reference arguments.
- **needs_dynamic_verification:** false

## 5. Unnamed tuple configurations derive names embedding module and type qualification

- **Severity:** medium
- **File:** `Sources/SnapshotTestingMacros/Assertion/DerivedSnapshotNames.swift:3`
- **Failure scenario:** `String(describing:)` of a bare enum value prints just the case name, but for a TUPLE Swift prints elements fully qualified, e.g. `"(SnapshotsIntegrationTests.Layout.compact, SnapshotsIntegrationTests.UserState.loggedIn)"`. An unnamed `SnapshotConfiguration` with a tuple value derives a name baking module and type names into the reference filename. The repo's own committed reference demonstrates it: `Tests/SnapshotsIntegrationTests/ExpectSnapshot/__Snapshots__/ExpectSnapshot+Configurations/tuple2/SnapshotsIntegrationTests-Layout-compact-SnapshotsIntegrationTests-UserState-loggedIn_tuple2_min-size_dark.1.png`. Renaming the test target, moving the enum to another module, or nesting it silently changes every derived tuple name — all such references orphan and tests re-record/fail en masse with no change to the values themselves.
- **Evidence:** `ExpectSnapshotAdapter.swift:35-43` (configurationName falls back to `DerivedSnapshotNames.argumentName(from: configuration.value)` — the whole tuple); `DerivedSnapshotNames.swift:2-5` (`String(describing:)` + normalize). Contrast in the same suite: `ExpectSnapshot+Argument/derivedArgumentName/zero_...` (unqualified scalar) vs the qualified tuple filename above.
- **Suggested fix:** In the `(A,B)`/`(A,B,C)` adapter overloads (`ExpectSnapshotAdapter.swift:561, 649`) derive the name per element (`argumentName(from: value.0) + "-" + argumentName(from: value.1) ...`) instead of describing the tuple as a whole; or emit a runtime warning suggesting explicit names when the derived name contains the module prefix.
- **needs_dynamic_verification:** false

## 6. Repetition-safety fork: @MainActor tests use pointfree's never-reset counter instance

- **Severity:** medium
- **File:** `Sources/SnapshotTestingMacros/Assertion/ExpectSnapshotAdapter.swift:787`
- **Failure scenario:** Which pointfree counter instance names the artifact depends on test isolation. Nonisolated test → `main.sync` hop → `Test.current == nil` inside the block → pointfree uses `_counter` and registers `CleanCounterBetweenTestCases` (an XCTest observer that resets `_counter` per test case), enabling correct in-process repetition mapping. `@MainActor` test → same-task branch → `Test.current != nil` → pointfree uses `File.counter`, the task-local's default process-global instance, which is never bound (this package doesn't use pointfree's `.snapshots` trait) and never reset by the observer (registration is skipped in this branch). Running a `@MainActor` snapshot test with Xcode repetitions: iteration 2 looks for `<testName>.2.png`, which doesn't exist, so it records a new reference or fails — exactly the regression the `SnapshotsIntegrationRepetitionTests` target exists to guard against, but that target's tests are all nonisolated so this `@MainActor` variant is untested.
- **Evidence:** `ExpectSnapshotAdapter.swift:787-796` (same-task branch keeps `Test.current` visible); vendored pointfree 1.19.1 `AssertSnapshot.swift:296-300` (`if Test.current == nil { CleanCounterBetweenTestCases.registerIfNeeded() }`), `:555-567` (counter selection), `:591-609` (observer resets only `_counter`), `SnapshotsTestTrait.swift:54` (only `File.$counter` binding, unused here). `Package.swift:151-155` documents the repetition target's purpose. `Tests/SnapshotsIntegrationRepetitionTests/ExpectSnapshotRepetitionTests.swift` is a nonisolated struct only.
- **Suggested fix:** Remove the counter dependency entirely by passing a stable `named:` (e.g. `"1"`) to `SnapshotTesting.verifySnapshot` in `PointfreeAsserter` so filenames become order/repetition-independent. Add a `@MainActor` test to the repetition target.
- **needs_dynamic_verification:** true

## 7. requireActiveTestContext crashes the whole test process for foreseeable misuse

- **Severity:** medium
- **File:** `Sources/SnapshotTestingMacros/Assertion/SnapshotRuntimePreconditions.swift:10`
- **Failure scenario:** Every `ExpectSnapshotAdapter.run` overload calls `requireActiveTestContext` at entry, which does `preconditionFailure` when `Test.current` is `nil`. `Test.current` is `nil` for XCTestCase methods (the exact scenario mid-migration from legacy pointfree `assertSnapshot`, expected given this branch ships a migration CLI) and for detached tasks/non-test threads. In both cases the entire test runner process aborts mid-suite, losing all other results, instead of failing one assertion. The package already contains a dual-mode reporter handling the XCTest case gracefully (`Asserter.swift:128-130` XCTFail fallback), inconsistent with the hard crash at the entry gate.
- **Evidence:** `SnapshotRuntimePreconditions.swift:8-14` (`preconditionFailure`); called from `ExpectSnapshotAdapter.swift:54, 76, 98, 120, 250, 284, 317, 351, 386, 448`. `Asserter.swift:98-131` shows the existing `#if canImport(Testing)`/`XCTFail` dual path proving the intent to support graceful reporting.
- **Suggested fix:** Replace `preconditionFailure` with an XCTFail-and-skip path when XCTest is loaded (`XCTCurrentTestCase` exists), keeping the crash only as last resort. At minimum document the crash and lock the message with a Swift Testing exit test (`#expect(processExitsWith:)`).
- **needs_dynamic_verification:** false

## 8. Low-severity naming warts: Optional stringification and SnapshotConfiguration.none artifact name

- **Severity:** low
- **File:** `Sources/SnapshotTestingMacros/SnapshotConfiguration/SnapshotConfigurationParser.swift:28`
- **Failure scenario:** (1) `SnapshotConfigurationParser.parse([T])` names each value `"\($0)"`; for `T == Optional<String>` a non-nil element stringifies as `Optional("x")` → normalized `"Optional-x"`, inconsistent with the documented convention of explicit names for optional configurations. (2) The public `SnapshotConfiguration.none` (Void value, name nil), if passed to `#expectSnapshot(configuration:)`, flows through `resolvedConfiguration` → `argumentName(from: ())` → `String(describing: ())` == `"()"` → normalization strips everything → fallback `"snapshot"`: the assertion silently gains a `"snapshot_"` testName prefix and per-test subfolder, diverging from the equivalent direct-value call. Also `.none` is declared as `static var none: SnapshotConfiguration<Void>` on the generic `SnapshotConfiguration<T>`, so `SnapshotConfiguration<Int>.none` resolves and returns a Void configuration.
- **Evidence:** `SnapshotConfigurationParser.swift:26-30`; `SnapshotConfiguration.swift:56-59` (public `static var none` on the generic type); `ExpectSnapshotAdapter.swift:35-43, 352`; `DerivedSnapshotNames.swift:4` (empty → `"snapshot"`); `AssertionRequestGenerator.swift:30-33` (non-nil configurationName switches to nested test-folder layout).
- **Suggested fix:** In `parse([T])`, unwrap Optionals for naming (nil → `"nil"`, some → describe the wrapped value). Special-case `Void` in `configurationName(for:)` to return nil so `.none` behaves like the no-configuration path. Constrain `none` to an extension where `T == Void`.
- **needs_dynamic_verification:** false

## 9. Hygiene and test-coverage gaps

- **Severity:** improvement
- **File:** `Sources/SnapshotsMacros/ExpectSnapshot/ExpectSnapshotMacro.swift:39`
- **Description:**
  1. Dead code: the third arm of makeValueClosure resolution (search `makeValueArguments` for a closure) is unreachable — every `ClosureExprSyntax` in `makeValueArguments` is also in `unlabeledArguments` and found first by `firstUnlabeledClosure`.
  2. The four `@unchecked Sendable` boxes in `ExpectSnapshotAdapter` are currently safe: the downstream pipeline invokes the boxed value/closure exactly once while the calling task is blocked in `DispatchQueue.main.sync`. `SizeAssertionRequestGenerator.makeSizes` calls `context.makeSnapshotView()` once (`SizeAssertionRequestGenerator.swift:74`) and reuses the single view controller for every size/theme request (line 30). This resolves the reader's escalation: `makeValue` runs exactly once per assertion, single-read-while-caller-blocked. Nothing at the type level enforces this, though — a future per-theme/per-size re-invocation of `makeSnapshotView` (a plausible fix direction for known bug #2, the AppKit appearance issue) would silently re-enter the user's non-Sendable closure off its original isolation. Worth a comment contract plus a once-flag trap.
  3. Macro-expansion tests cover only clean shapes; missing: function-reference `makeValue`, trailing-comment trivia, `named:` with string interpolation, unlabeled closure argument plus trailing closure (trailing silently wins today), `#expectSnapshot(argument:)` with an extra unlabeled non-closure argument (silently dropped).
  4. Surface note: the macro declaration takes `_ value: V` but the expansion calls `__expectSnapshot(_ value: sending V)`, so region-isolation errors surface only post-expansion with `__`-prefixed internals in the diagnostic.
- **Evidence:** `ExpectSnapshotMacro.swift:36-41` (dead third arm; `firstUnlabeledClosure` at `:13-16` searches the superset); `ExpectSnapshotAdapter.swift:5-32` (boxes without synchronization/once-semantics); `SizeAssertionRequestGenerator.swift:74` and `26-36` (single `makeSnapshotView` call, instance reuse across all requests); `expectSnapshot.swift:5-6` vs `ExpectSnapshotMacroDefinition.swift:4-7` (sending only on the runtime function); `Tests/SnapshotsUnitTests/ExpectSnapshot/ExpectSnapshotMacroTests.swift` + `ExpectSnapshotClosureMacroTests.swift` (happy-path shapes and the missing-value diagnostic only).
- **Suggested fix:** Delete the dead arm or replace it with a "multiple closures supplied" diagnostic; add a read-once trap to the boxes; add the listed `assertMacro` cases.
- **needs_dynamic_verification:** false
