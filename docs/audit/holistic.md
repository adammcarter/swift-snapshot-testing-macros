# Audit findings: holistic

Holistic static review of the `snapshot-helpers` branch (no builds run). Verified-clean areas: the `#expectSnapshot` overload set in `ExpectSnapshotMacroDefinition.swift` matches README/Usage/Parameterised/Traits docs overload-for-overload (SwiftUI direct/closure/argument/configuration incl. tuple-2/3; UIKit/AppKit direct-value only); deprecation annotations on all `@SnapshotSuite`/`@SnapshotTest` overloads are complete and match the docs' framing; `Package.swift` and `Package@swift-6.2.swift` are byte-identical past line 1 (check-packages is wired into `mise run lint`); `mise.toml` matches CONTRIBUTING/README commands; trait task-local defaults (`.theme(.all)`, `.sizes(.minimum)`, `.strategy(.image)`, `.record(.missing)`, `.diffTool(.default)`) match documented defaults; `named:`/configuration naming semantics match Parameterised.md. Findings below are ordered most-severe first. Two known bugs (task-pointer-keyed context cache; migration rewriter non-compiling if/switch output) are referenced for interaction context only and are not re-reported here.

## 1. [HIGH] Migration rewriter silently deletes the arguments of a pre-existing `@Suite` attribute when deduping `@Suite` + `@SnapshotSuite`

- **File**: `Sources/SnapshotMigrationSupport/Rewriting/SnapshotMigrationRewriter.swift:1052`
- **Failure scenario**: Input `@Suite("Profile cards", .serialized)` + `@SnapshotSuite(.theme(.light))` (the legacy pattern shown in MIGRATION.md's own "Before" example) migrates to just `@Suite(.theme(.light))` — the display name and `.serialized` (or `.tags`, `.enabled(if:)`, etc.) are silently dropped. Output compiles, `reasons` is empty, file counted as migrated, and `--apply` writes it. Tests relying on `.serialized` start running in parallel (flaky snapshots); suite display names vanish with no report signal.
- **Evidence**: `SnapshotMigrationRewriter.swift:1040-1060` — `removeDuplicateSuiteAttributeIfNeeded` matches any attribute named `Suite` and appends a `TextEdit` covering the whole `AttributeSyntax` (including its argument list) with replacement `""`, with no check that the removed `@Suite` is argument-free. The rename edit at `:1027-1035` only replaces the `SnapshotSuite` name token. Both existing dedup tests use a bare `@Suite` only: `Tests/SnapshotsUnitTests/Migration/SnapshotMigrationRewriterCoreTests.swift:58-76` and `SnapshotMigrationRewriterParameterizedTests.swift:305-328` — the argument-carrying case is untested.
- **Suggested fix**: Only remove the duplicate `@Suite` when `attribute.arguments == nil`; when it has arguments, either keep the argful `@Suite` and delete `@SnapshotSuite` instead (folding legacy snapshot traits into the surviving attribute's argument list), or emit a skip reason (e.g. `unsupported-attribute-arguments`) so the file is left untouched and surfaced in the report.
- **needs_dynamic_verification**: false

## 2. [HIGH] Configurations `.init` shorthand regex corrupts receiver-qualified and nested value inits, producing non-compiling applied output

- **File**: `Sources/SnapshotMigrationSupport/Rewriting/SnapshotMigrationRewriter.swift:593`
- **Failure scenario**: `expandSnapshotConfigurationInitializerShorthand` rewrites `.init(` to `SnapshotConfiguration(` anywhere in the configurations argument expression whenever the next label is `name:` or `value:`. This also matches receiver-qualified inits (`value: User.init(name: "Bob")` → `value: UserSnapshotConfiguration(name: "Bob")`, undeclared type) and contextual value inits (`.init(name: "a", value: .init(name: "Bob"))` has its inner init corrupted). `addConfigurationInitializerTypeContext` then string-replaces every `SnapshotConfiguration(` occurrence (including corrupted ones and the substring inside `UserSnapshotConfiguration(`) with `SnapshotConfiguration<T>(`. Any legacy `configurations:` array whose value expressions construct a model with a first parameter labelled `name:` or `value:` (common) is rewritten into non-compiling code, reported as migrated with zero reasons, and written by `--apply`.
- **Evidence**: `SnapshotMigrationRewriter.swift:591-603` — regex `\.init\s*\((?=\s*(?:name:|value:))` has no guard on the preceding character (identifier char ⇒ receiver-qualified init) and no nesting awareness; `:640-648` `addConfigurationInitializerTypeContext` does a plain `replacingOccurrences(of: "SnapshotConfiguration(")`. Call path `rewriteConfigurationsArgumentsExpression` (`:605-622`) runs for every `configurations:` migration on both SwiftUI and UIKit platforms. No test in `SnapshotMigrationRewriterParameterizedTests.swift` covers a value expression using `.init(name:` or `Type.init(name:` — only the intended shorthand is tested (lines 106-148, 218-260).
- **Suggested fix**: Replace the regex/string pass with a SwiftSyntax-based rewrite: only rewrite `FunctionCallExprSyntax` nodes whose callee is a bare `.init` member access with no base expression AND whose position is a direct element of the top-level array literal (or direct return of the map closure). Scope the `SnapshotConfiguration(` → `SnapshotConfiguration<T>(` replacement to those same rewritten call sites.
- **needs_dynamic_verification**: false

## 3. [MEDIUM] Migration report counts files but labels everything "declarations" across console, JSON schema, and docs

- **File**: `Sources/SnapshotMigrationSupport/Runner/MigrationRunner.swift:187`
- **Failure scenario**: A file with ten `@SnapshotTest` functions where one is unsupported is reported as "1 skipped declaration" while ten tests were left unmigrated (the runner is all-or-nothing per file: any skip reason discards the whole file's rewrite). Users tracking rollout progress and CI gating on `--fail-on-skips` get a systematically wrong picture of remaining work. Files that merely contain the substring `@SnapshotTest` (e.g. in a comment) become candidates and are counted as skipped with no issue line, permanently inflating skip counts under `--fail-on-skips`.
- **Evidence**: `MigrationRunner.swift:66-117` — per-file loop, one increment per file per outcome; `:187` `let candidateDeclarations = scan.candidateFiles.count`; `:192` percentage computed over files. `ConsoleReporter.swift:9-12` prints the "declarations" labels; `ConsoleReporterTests.swift:37` bakes the label in. README.md:59 and MIGRATION.md:132 promise "a summary of migrated, skipped, and failed declarations." `ProjectScanner.swift:59` treats substring matches as candidates; `MigrationRunner.swift:85-88` counts non-changed files as skipped with no issue.
- **Suggested fix**: Extend `RewriteResult` with per-declaration counts (from `collector.legacyFunctions`), aggregate those in the runner for the `*Declarations` fields, and keep existing per-file counters under file-named fields. Update `ConsoleReporter` labels and README/MIGRATION wording to match whichever unit is reported.
- **needs_dynamic_verification**: false

## 5. [MEDIUM] `ApplyLock` stale-lock reclamation race can grant the apply lock to two concurrent processes

- **File**: `Sources/SnapshotMigrationSupport/Applying/ApplyLock.swift:58`
- **Failure scenario**: A previous `--apply` crashed leaving a stale lock; two new `--apply` runs A and B start concurrently. Both fail `O_EXCL`, both read the stale PID, both get `ESRCH`. A unlinks the stale lock, loops, creates a fresh lock it now owns. B then unlinks that same path (unlink succeeds regardless of file identity), loops, and creates its own lock. Both processes now believe they hold the exclusive apply lock and run `AtomicFileReplacer` concurrently over the same project — the per-file SHA-256 precondition limits damage to precondition failures/interleaved state rather than corruption, but mutual exclusion is broken exactly in the crashed-previous-run case the lock exists for.
- **Evidence**: `ApplyLock.swift:22-45` acquire loop (`O_CREAT|O_EXCL`, then `if reclaimStaleLockIfNeeded(atPath:) { continue }`); `:53-62` reclaim reads owner text, checks `kill(pid, 0) == -1 && errno == ESRCH`, then `unlink(path)` with no identity re-check between read and unlink. `ApplySafetyTests.swift:36-46` tests single-process stale reclamation only; no concurrent-reclaim test exists.
- **Suggested fix**: Make reclamation identity-safe — `fstat` the existing lock file, re-`lstat` the path and compare `(dev, inode)` before unlinking — or switch to `flock(fd, LOCK_EX|LOCK_NB)` on an `O_CREAT` (not `O_EXCL`) descriptor so staleness is handled by the kernel with no unlink race.
- **needs_dynamic_verification**: false

## 6. [MEDIUM] Default dry-run permanently accumulates staged copies under /tmp; five CLI flags, the exit-code ladder, and `--help` are undocumented/broken

- **File**: `Sources/SnapshotMigrationSupport/Runner/MigrationRunner.swift:90`
- **Failure scenario**: Staging is gated on `mode == .apply || mode == .dryRun || keepTemp` — since `MigrationMode` has only those two cases, the condition is always true and every run stages full rewritten copies under `/tmp/snapshot-migration/<runID>/`. Cleanup only happens on a fully successful `--apply`, so the documented default mode (dry-run) leaves a new permanent directory per run, and the docs' own rollout loop (dry-run, fix, apply, re-dry-run) multiplies them; nothing prints the staging path in dry-run. Separately, `--keep-temp`, `--fail-on-skips`, `--max-file-size-bytes`, `--max-staged-bytes`, `--apply-lock-timeout-seconds`, and exit codes 1-4 appear in no documentation, and `--help` is rejected as `unknown option --help` (exit 3). Console output truncates issues at 50 with no "N more" marker.
- **Evidence**: `MigrationRunner.swift:90` (always-true staging condition; `MigrationMode` has only `dryRun`/`apply` in `CLI/MigrationOptions.swift:1-4`); `:179-185` removal only when `mode == .apply && !keepTemp && !hadMigrationFailures && !hadApplyFailures`; `RunStagingStore.swift:20-26` hardcodes the /tmp path; intentional per `MigrationRunnerIntegrationTests.swift:9-51` but undocumented. `rg` for the flag names over all `*.md` returns nothing; `rg -i 'help|usage'` over the CLI sources returns nothing; `MigrationOptionsParser.swift:52-53` default-cases unknown options including `--help` with no help handling. `ConsoleReporter.swift:27` / `main.swift:12` (`maxIssues` truncation with no continuation marker).
- **Suggested fix**: Either stop auto-staging in dry-run unless `--keep-temp` is passed, or keep staging but remove the run directory at the end of dry-run unless `--keep-temp`, printing the staging path when kept. Add `--help`/usage text listing all flags and exit codes; document flags/exit codes/temp-dir behaviour in README.md/MIGRATION.md; print a "and N more issues" marker when truncating.
- **needs_dynamic_verification**: false

## 7. [LOW] No platform guard for watchOS/tvOS/visionOS — unsupported-platform consumers hit confusing compile errors inside `UniversalTypes`

- **File**: `Sources/SnapshotTestingMacros/_Convenience/UniversalTypes.swift:3`
- **Failure scenario**: `Package.swift` declares `[.macOS(.v15), .iOS(.v15)]` only, but SPM does not prevent building for platforms absent from the list. `UniversalTypes` resolves purely via `#if canImport(UIKit)/#elseif canImport(AppKit)/#else #error`. On watchOS, `canImport(UIKit)` is true but the watchOS UIKit surface lacks `UIView`/`UIViewController`/`UIHostingController`, so a consumer that includes this library for a watchOS target gets "cannot find type UIView in scope" deep inside this package rather than a clear "platform not supported" — the `#error` fallback never fires because the `canImport` check passes.
- **Evidence**: `Package.swift:8-11` (platforms list); `UniversalTypes.swift:3-25` (`#if canImport(UIKit)` typealiases; unreachable `#else #error` on watchOS). No `#if os(watchOS)` guard anywhere in `Sources` (`rg` for `os(watchOS)` returns nothing). README/docs never state supported platforms beyond the UIKit/AppKit table.
- **Suggested fix**: Add an explicit guard, e.g. `#if os(watchOS) || os(tvOS) || os(visionOS)` `#error("SnapshotTestingMacros supports iOS and macOS only")` `#endif`, and state the supported platform set in README.md.
- **needs_dynamic_verification**: true (exact watchOS SDK surface not confirmed by static reading alone)

## 9. [LOW] `#expectSnapshot` outside the active Swift Testing task crashes the whole process via `preconditionFailure` — undocumented

- **File**: `Sources/SnapshotTestingMacros/Assertion/SnapshotRuntimePreconditions.swift:10`
- **Failure scenario**: Every adapter entry point calls `requireActiveTestContext(Test.current)`, which `preconditionFailure`s when `Test.current` is nil — true for assertions inside `Task.detached {}` within a test, and for any XCTest-hosted usage of `#expectSnapshot`. Instead of one failing test, the entire test runner process aborts, taking all other suites' results with it. Neither README.md, Usage.md, nor MIGRATION.md mentions that the native surface is Swift-Testing-only at runtime or that detached tasks hard-crash.
- **Evidence**: `SnapshotRuntimePreconditions.swift:8-14`; called at every adapter entry point (`ExpectSnapshotAdapter.swift:54, 76, 98, 120, 250, 284, 317, 351, 386, 448`). `rg` for `detached|XCTest` over README.md/Documentation/*.md/MIGRATION.md returns nothing relevant.
- **Suggested fix**: Document the constraint (Swift Testing only, no detached tasks, misuse aborts the process). Longer term, once the execution-context cache is reworked, consider `Issue.record(...)` + return instead of a hard abort, provided a skipped assertion cannot silently pass.
- **needs_dynamic_verification**: false

## 10. [LOW] `SnapshotExecutionContext` cache grows unboundedly for the life of the process

- **File**: `Sources/SnapshotTestingMacros/Assertion/TaskLocalSnapshotExecutionContext.swift:54`
- **Failure scenario**: Interaction note with confirmed known bug (task-pointer-keyed cache reuses stale contexts on recycled task pointers): the cache keyed by `(testID, caseIdentity, taskPointer)` inserts an entry per test/case/task and never removes anything. Memory grows monotonically across a large run (a 10k-case parameterised suite retains 10k entries + `usedNames` sets until process exit), and the lack of eviction is precisely why recycled task pointers collide with stale entries in the known cache bug — any fix to that bug should introduce scoped lifetime rather than patching the key alone.
- **Evidence**: `TaskLocalSnapshotExecutionContext.swift:30-36` (cache dictionary), `:54-63` and `:86-94` (insert-only under lock in both sync/async paths); no `removeValue`/`removeAll` anywhere in the file or its callers. `SnapshotExecutionContext.swift:3-35` shows each cached context also retains a growing `usedNames` Set.
- **Suggested fix**: When fixing the stale-context cache bug, give the cache bounded lifetime: derive identity solely from `(Test.ID, Test.Case identity)` without the raw task pointer, and evict when the outermost `withCurrent` scope for that test case completes.
- **needs_dynamic_verification**: false
