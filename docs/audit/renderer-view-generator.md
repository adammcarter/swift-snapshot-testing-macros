# Audit findings: renderer-view-generator

Static review (cross-checked against vendored pointfree swift-snapshot-testing 1.19.1 sources) of the renderer / view-generator machinery — decorator, container wrapping, sizing, and the strategy hand-off to `.image`/`.recursiveDescription`. Verified-sound: decorator inset math and containment call order, `TaskLocal` decorator config surviving the `DispatchQueue.main.sync` hop, UIKit per-request re-hosting/re-layout/theme+scale application (iOS light/dark refs genuinely differ), no retain cycles or leaked windows, and main-actor isolation of `UIWindow()`/generator statics. Real defects cluster on two axes: AppKit fidelity (background trait is a no-op, no re-hosting/scale on macOS) and measurement destroying frame-based sizing (`embedChild` forcing `translatesAutoresizingMaskIntoConstraints = false`). None of these re-report the six known bugs, though several interact with known bug #2 (AppKit `NSAppearance` never applied).

## 1. `.backgroundColor(...)` trait is a silent no-op on macOS: decorator container `NSView` is never layer-backed

- **Severity:** high
- **File:** `Sources/SnapshotTestingMacros/_Convenience/AppKit+Convenience.swift:17`
- **Failure scenario:** `@Test(.backgroundColor(.red)) func f() { #expectSnapshot(Text("x")) }` run on macOS records a fully transparent container behind the text; the trait silently does nothing. No error, no crash — macOS references are recorded wrong and stay green forever.
- **Evidence:** (1) `SnapshotViewGenerating+makeDecoratedView.swift:17-19` applies the trait via `$0.view.backgroundColor = configuration.backgroundColor` on the container from `wrappingInContainerViewController`. (2) That container is a bare `SnapshotViewController()` = `NSViewController()` on AppKit (`SnapshotView+wrappingInContainerView.swift:11`); its nib-less auto-created `NSView` has `wantsLayer == false`, so `view.layer == nil`. (3) The only AppKit `backgroundColor` accessor is `AppKit+Convenience.swift:14-19`: `set { layer?.backgroundColor = newValue?.cgColor }` — with `layer == nil` the optional-chained write is a no-op. (4) `rg wantsLayer` across `Sources/` and `Tests/` returns zero hits. On UIKit every `UIView` is layer-backed so the same code works on iOS — a genuine platform divergence, distinct from but compounding known bug #2 (NSAppearance never applied). The only integration test for this trait (`background-red` in `Tests/SnapshotsIntegrationTests/ExpectSnapshot/ExpectSnapshot+Traits.swift:21-24`) runs on iPhone only.
- **Suggested fix:** Make the setter self-sufficient: `set { wantsLayer = true; layer?.backgroundColor = newValue?.cgColor }` (or set `parentViewController.view.wantsLayer = true` in `wrappingInContainerViewController` under `#if canImport(AppKit)`). Once known bug #2 is fixed, resolve dynamic colors inside `NSAppearance.performAsCurrentDrawingAppearance` or via an `NSView` subclass drawing in `updateLayer`.
- **needs_dynamic_verification:** false

## 2. `embedChild` unconditionally sets `translatesAutoresizingMaskIntoConstraints = false`, destroying frame-based sizing; with a padding trait this records a silent empty snapshot

- **Severity:** high
- **File:** `Sources/SnapshotTestingMacros/_Convenience/SnapshotView+wrappingInContainerView.swift:40`
- **Failure scenario:** Any payload sized by frame rather than Auto Layout (a plain frame-laid-out `UIView`/`NSView` via the `#expectSnapshot(UIView)` overload, or a `UIViewController` whose root view has no intrinsic size/constraints — common in views migrated from pointfree where `assertSnapshot(of: view, as: .image)` used the view's frame) collapses to zero under the default `.sizes(.minimum)` measurement. Bare: `SizeError.zeroSize` even though the view has a valid 200x100 frame. With `.padding(.all, 16)`: compressed size becomes 32x32 (insets only), all zero-size guards pass, and a 32x32 reference containing an invisible zero-sized payload is silently recorded and compares green forever.
- **Evidence:** (1) `#expectSnapshot(UIView)` wraps the raw view via `$0.view = view` (`SnapshotViewGenerator+UIView.swift:19-21`), preserving no size metadata. (2) Default sizes are `[.init(width: .minimum, height: .minimum)]` (`SizesSnapshotTrait.swift:23-25`), routing through `compressedSizeWhenConstrained()` (`SizeAssertionRequestGenerator.swift:143-163`), which calls `embedChild` — line 40 sets TAMIC=false unconditionally and pins edges. With TAMIC=false the view's frame contributes nothing to layout; a frame-based view has no intrinsic content size and no internal constraints, so `systemLayoutSizeFitting(layoutFittingCompressedSize)`/`fittingSize` solves to 0x0. (3) Bare case: guards at `SizeAssertionRequestGenerator.swift:84-94` throw `SizeError.zeroSize`. (4) Padded case: the decorator wraps first (`makeDecoratedView.swift:17`, insets 16), so container = child(0) + 32 in each dimension = 32x32, passing the `> 0` guards and rendering. The TAMIC mutation also permanently mutates the user's own view object. Fixed-size traits (`.sizes(.fixed(...))`) bypass embedding (`SizeAssertionRequestGenerator.swift:127-129`) and work — the only workaround.
- **Suggested fix:** Fall back to the payload view's pre-existing `bounds.size` when the compressed fit comes back zero in a dimension, or measure the CHILD's compressed size (not the container's) and error loudly even in the padded case. Restore the original `translatesAutoresizingMaskIntoConstraints` value after measurement.
- **needs_dynamic_verification:** true

## 3. AppKit image path never re-hosts or re-lays-out the view at the request size — multi-size/fixed-size and scale are structurally broken on macOS

- **Severity:** high
- **File:** `Sources/SnapshotTestingMacros/Assertion/RequestGenerator/Generators/StrategyAssertionRequestGenerator.swift:53`
- **Failure scenario:** On macOS the computed per-request size is only ever applied as a raw `view.frame.size` poke by pointfree's `NSView` strategy — no window hosting, no constraint re-pinning, no forced layout pass — while iOS fully re-hosts in a fresh sized `UIWindow` with fresh constraints and `layoutIfNeeded` per request. (a) `.sizes(.minimum, .fixed(width: 390, height: 844))` — all permutations render the SAME shared view controller whose subtree was last laid out inside a transient zero-frame sizing container; correctness depends on undocumented `cacheDisplay` layout behavior and autorelease timing of the transient container — stale, blank, or wrong-size content is likely. (b) `.sizes(.fixed(..., scale: 2))` — `Size.scale`/`windowScale` are computed then silently dropped: the AppKit branch calls `.image(size: size)` which has no traits/scale parameter, so scale does nothing on macOS while working on iOS.
- **Evidence:** (1) One decorated VC is created once and shared by every `SizePair` (`SizeAssertionRequestGenerator.swift:74`, `:99`, `:30`). (2) Each `.minimum` measurement embeds that VC into a NEW transient container (`SizeAssertionRequestGenerator.swift:148-149`) whose auto-created `NSView` has frame `.zero`; `fittingSize` yields the ideal number but laid-out frames in the subtree remain at the zero-frame container's solution. (3) `StrategyAssertionRequestGenerator.swift:50-60` uses pointfree `Snapshotting<NSViewController, NSImage>.image(size:)`, which is the `NSView` strategy pulled back on `$0.view` (`.build/checkouts/swift-snapshot-testing/Sources/SnapshotTesting/Snapshotting/NSViewController.swift:20-26`): `view.frame.size = size` then `bitmapImageRepForCachingDisplay`/`cacheDisplay` (`.../NSView.swift:26-46`) — no `prepareView`, no window, no layout. (4) Compare UIKit: pointfree `prepareView`/`add` (`.../Common/View.swift:929-1075`) re-hosts in a per-request sized `Window`, re-pins, sets override traits, calls `layoutIfNeeded` — per-size correctness guaranteed. (5) `displayScale` is used only inside `#if canImport(UIKit)` `makeTraits()` (`StrategyAssertionRequestGenerator.swift:67-82`); AppKit has no equivalent. Distinct geometry/scale gap on top of known bug #2; zero macOS runtime coverage exists to catch it (all 85 reference PNGs are iOS `min-size`).
- **Suggested fix:** Build an AppKit equivalent of pointfree's UIKit `prepareView`: detach the view, host it in an offscreen `NSWindow` sized to the request (matching `backingScaleFactor` to `Size.scale`), and run `layoutSubtreeIfNeeded` before rendering — ideally alongside the NSAppearance fix for known bug #2.
- **needs_dynamic_verification:** true

## 4. `.recursiveDescription` strategy drops the computed size, theme, and scale — permutation-named refs with identical/mismatched content

- **Severity:** medium
- **File:** `Sources/SnapshotTestingMacros/Assertion/RequestGenerator/Generators/StrategyAssertionRequestGenerator.swift:25`
- **Failure scenario:** With `@Test(.strategy(.recursiveDescription), .theme(.all))` the pipeline still fans out per size/theme and names reference files accordingly (e.g. `..._min-size_light.1.txt`, `..._min-size_dark.1.txt`), but the strategy is constructed as bare `.recursiveDescription` with no size/traits — light and dark files are byte-identical, and dumped frames don't match the size named in the file (UIKit: stale programmatic view frame, not computed min size; AppKit: never laid out, frames dump as zero). Users get N misleadingly-named duplicate references.
- **Evidence:** `StrategyAssertionRequestGenerator.swift:22-33` — the `.recursiveDescription` branch ignores `size`/`theme`/`displayScale` entirely (only consumed in the `.image` branch, lines 35-61). Theme fan-out: `ThemeAssertionRequestGenerator.swift:15-33`; name components appended regardless of strategy: `NameAssertionRequestGenerator.swift:42-51`. Pointfree offers `Snapshotting<UIViewController, String>.recursiveDescription(on:size:traits:)` (`.../UIViewController.swift:140-163`) which applies both; the AppKit variant (`NSViewController.swift:29-35`) never lays out at all.
- **Suggested fix:** Pass `.recursiveDescription(size: size, traits: makeTraits())` on UIKit; force a layout at `size` on AppKit before dumping. Alternatively collapse the theme fan-out for text strategies to one reference per size.
- **needs_dynamic_verification:** true

## 5. Availability check names only iOS for an API that is version-gated on macOS too

- **Severity:** low
- **File:** `Sources/SnapshotTestingMacros/SnapshotViewGenerator/SnapshotViewGenerator+SwiftUI.swift:34`
- **Failure scenario:** `if #available(iOS 16.0, *)` guards `controller.sizingOptions`, but on macOS the `*` wildcard makes the branch unconditionally true regardless of OS version, while `NSHostingController.sizingOptions` only exists on macOS 13+. Harmless today only because `Package.swift` pins `.macOS(.v15)`; lowering the deployment target below 13 would misexpress intent (or fail to compile).
- **Evidence:** `SnapshotViewGenerator+SwiftUI.swift:34-36`; `SnapshotHostingController` = `NSHostingController` on AppKit (`UniversalTypes.swift:20`); platform floor `.macOS(.v15)` in `Package.swift`.
- **Suggested fix:** Write `if #available(iOS 16.0, macOS 13.0, *)` to state the real dependency.
- **needs_dynamic_verification:** false

## 6. UIView entry point assigns the controller's view directly, bypassing the loadView/viewDidLoad lifecycle

- **Severity:** low
- **File:** `Sources/SnapshotTestingMacros/SnapshotViewGenerator/SnapshotViewGenerator+UIView.swift:19`
- **Failure scenario:** `with(SnapshotViewController()) { $0.view = view }` marks the controller's view as loaded without the documented `loadView()`/`viewDidLoad()` sequence. Currently latent (the bare container has no lifecycle overrides to skip), but any future setup logic added to a custom container controller's `viewDidLoad` would silently never run for the raw-view entry point; the AppKit equivalent skips `NSViewController.viewDidLoad` too. Today's behavior is correct by luck, not contract.
- **Evidence:** `SnapshotViewGenerator+UIView.swift:16-22`. The SwiftUI path (`SnapshotViewGenerator+SwiftUI.swift:31`) and generic path use real controller initializers; only this overload bypasses the lifecycle.
- **Suggested fix:** Use a tiny container controller with `loadView() { view = injectedView }` (store the view before load), or document that the wrapper controller must remain lifecycle-free.
- **needs_dynamic_verification:** false

## 7. Coverage gap: no runtime tests for the decorator/wrapping/sizing machinery; zero macOS coverage; zero non-min-size references

- **Severity:** improvement
- **File:** `Tests/SnapshotsIntegrationTests/ExpectSnapshot/ExpectSnapshot+Traits.swift:21`
- **Failure scenario:** The only runtime exercise of `makeDecoratedView`/`wrappingInContainerViewController`/`embedChild`/the strategy hand-off is the iOS-device integration suite: all 85 checked-in reference PNGs are iOS `min-size` variants; unit-test hits for "SnapshotViewGenerator" are macro-expansion text assertions only. Nothing would catch the AppKit-only defects above (findings 1 and 3) or known bug #2; fixed-size/device-size/scale-override/multi-size fan-out paths have no reference-based coverage on any platform; decorator container math has no isolated unit test.
- **Evidence:** `fd -e png Tests | rg -v min-size` returns nothing (85/85 refs are `min-size`, all iOS); `Package.swift` documents `SnapshotsIntegrationTests` as "must be run on an iPhone 17"; `rg makeDecoratedView|wrappingInContainerViewController|embedChild` over `Tests/` matches only macro-expansion string fixtures in `SnapshotsUnitTests`.
- **Suggested fix:** Add a macOS CI destination for the traits/decorator integration tests, an integration test locking the multi-size/scale fan-out, and main-actor unit tests for `wrappingInContainerViewController`/`embedChild` asserting child frame geometry after forced layout and (AppKit) background color application.
- **needs_dynamic_verification:** false
